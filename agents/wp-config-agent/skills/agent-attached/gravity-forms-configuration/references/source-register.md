## Source-use rules

- Prefer official Gravity Forms docs for behaviour, fields, add-ons, settings, REST API, security, privacy, accessibility, and troubleshooting.
- Use product pages and template pages for workflow patterns, not as proof that a specific field/add-on/feed exists on a live site.
- Use third-party add-on sources only after the site preflight confirms the plugin is installed, active, licensed where applicable, and supported.
- Mark Gravity Forms 3.0 behaviour as beta/version-specific unless the target site is confirmed to run a compatible 3.0 build and the user accepts beta risk.
- Re-run source review before changing payment, user registration, retention, upload, REST/API, or production publishing behaviour on a live site.

## Compatibility-pass source notes

- Gravity Forms documents current preferred and minimum environment requirements and notes that requirements can change, so the skill records environment findings as time-sensitive and recommends current system-status checks before live work.
- Gravity Forms notification guidance separates entry creation from email delivery, so the skill now treats missing emails as a delivery investigation until notification config, SMTP, DNS, and logs are reviewed.
- Gravity Forms logging docs warn that logs can contain personal data in plain text, so the skill now requires temporary logging, redaction, and post-investigation cleanup notes.
- Gravity Forms upload guidance confirms the File Upload field is constrained by WordPress core upload and MIME validation, so the skill now blocks broad upload defaults and requires an approved extension/retention stance.
- Gravity Forms cache guidance identifies caching and script optimisation as common causes of dynamic form failures, so the skill now adds cache/CDN/script exclusion checks to troubleshooting and production embed planning.

## Feed and lifecycle source notes

- Feed processing depends on active feed state, add-on connection, conditional logic, field mappings, spam status, and background processing/log evidence.

- Entry data, Save and Continue drafts, Partial Entries, uploaded files, IP addresses, and add-on destinations need a data-lifecycle stance before retention or export/erase changes.

## Conditional/dynamic/webhook source notes

- Dynamic population can be configured through query strings, shortcode field values, the Gravity Forms block Field Values setting, or PHP hooks. Hook-based population requires developer routing unless the active toolchain safely supports code changes.
- Dynamic population uses PHP and may not work correctly on cached pages; the skill must check cache/CDN behaviour before using dynamic field values on live pages.
- Conditional logic can affect fields, pages, notifications, confirmations, and feeds; the skill now requires a dependency map and branch test coverage for live logic changes.
- Pricing fields can support quote generators, donations, and order-like forms, but payment-linked calculations remain high risk and require sandbox/feed validation.
- The Webhooks Add-On can send remote HTTP requests on form submission and supports URL, method, format, headers, body, selected fields, and conditions; the skill now prefers selected fields and redacted evidence rather than All Fields or exposed secrets.
