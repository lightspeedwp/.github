Use this only when the user asks for a new form or major restructure and required inputs are missing. Keep intake short; ask only for blockers, otherwise use safe defaults and label assumptions.

## Minimum viable inputs

1. Site/environment and whether MCP access is available.
2. Form purpose and target audience.
3. Required outcome after submission.
4. Required fields and any fields to avoid collecting.
5. Notification recipients or routing rules.
6. Confirmation experience.
7. Embed target page or manual embed preference.
8. Add-ons needed or known to be installed.
9. Privacy/consent and retention expectations.
10. Testing owner and launch timing.

## Safe defaults when the user cannot answer

- Draft configuration mode only.
- Short form with visible labels, clear descriptions, consent where personal data is collected, and layered spam protection.
- Admin notification to a role/inbox placeholder, not an invented email address.
- User confirmation text rather than redirect unless a destination is supplied.
- No payment, user registration, file uploads, webhooks, or third-party feeds unless explicitly scoped and available.
- Manual implementation plan when MCP write actions are unavailable.

## One-question triage

When only one question is allowed, ask:

> What should happen operationally after someone submits this form: who receives it, what system/feed should it trigger, and what should the visitor see next?

## Intake output

Return a compact intake summary:

- Confirmed facts
- Assumptions
- Missing blockers
- Proposed safe defaults
- Risk level
- Recommended next output: preflight, configuration plan, change plan, or manual implementation plan
