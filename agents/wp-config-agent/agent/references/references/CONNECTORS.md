Use this guide to understand which attached apps and runtime tools the WordPress Configuration Agent should use, what evidence they provide, and when files or Memory are a better source.

## WordPress website connection

The agent currently has two WordPress apps attached for different environments:

- `LS Agency Dev Site` for development, staging, sandbox, testing, and pre-release work
- `LS Agency LIVE MCP` for live-site inspection, published-state checks, and explicitly requested live-site work

Choose the app that matches the environment named or implied by the user. If the environment is unclear, ask one short clarification question before site-specific inspection or implementation.

### LS Agency Dev Site

#### What it is used for

- inspecting development and staging site state
- checking draft configuration, plugins, content structures, options, users, comments, media, themes, and code-level files where supported
- carrying out supported implementation work before release
- validating staging-safe changes and pre-release behaviour

#### Evidence it provides

- direct current-state evidence from the development or staging environment
- draft plugin and theme state
- development content and settings evidence
- theme, plugin, and file-level evidence where the available actions support it

#### Practical usage boundaries

- treat this as the primary source for development, staging, sandbox, and pre-release verification
- prefer this app when the user refers to staging, development, sandbox, testing, or safe pre-release changes
- inspect here before recommending or applying draft changes when direct access is available
- do not assume that staging state matches the public site exactly

#### When to prefer files or Memory instead

- prefer `memory/` for durable project continuity and known defaults
- prefer `references/`, `templates/`, and `examples/` for standing guidance and reusable structures
- use app calls for current development evidence, not for long-term documentation storage

### LS Agency LIVE MCP

#### What it is used for

- inspecting current public WordPress site state
- checking live configuration, published content, taxonomies, comments, media, and supported settings
- carrying out explicitly requested live-site work where the app supports it

#### Evidence it provides

- direct current-state evidence from the live WordPress environment
- published content and settings evidence
- live plugin state where supported
- live media and metadata evidence where the available actions support it

#### Practical usage boundaries

- treat this as the primary source for live-site verification and published-state checks
- prefer this app when the user refers to the live site, production, the public site, published content, or current public behaviour
- treat live writes, plugin changes, file changes, theme changes, and database actions as higher-risk operations
- do not assume unsupported plugin control or unsupported environment access

#### When to prefer files or Memory instead

- prefer `memory/` for durable project continuity and known defaults
- prefer `references/`, `templates/`, and `examples/` for standing guidance and reusable structures
- use app calls for live evidence, not for long-term documentation storage

## Google Drive

### What it is used for

- reading or updating Docs, Sheets, Slides, and file metadata when Drive assets materially support the WordPress task

### Evidence it provides

- working documents, spreadsheets, presentations, comments, and shared file context

### Practical usage boundaries

- use it when the task depends on Drive-hosted source material
- do not treat Drive as proof of current live WordPress state unless the content itself is authoritative evidence

### When to prefer files or Memory instead

- prefer agent files for stable built-in reference material the agent should always carry
- prefer Memory for durable project continuity across sessions
- use Drive when the source lives externally and needs to be read or updated there

## GitHub

### What it is used for

- repository inspection
- code review for themes, plugins, or configuration files
- PR, commit, and issue context tied to WordPress implementation work

### Evidence it provides

- repository-backed code and history evidence
- PR and commit context
- file-level implementation details from source control

### Practical usage boundaries

- treat GitHub as code and change-history evidence, not as proof of live site configuration
- use it when the WordPress task depends on repository state or implementation history

### When to prefer files or Memory instead

- prefer agent files for stable operational guidance
- prefer Memory for durable continuity and decisions
- use GitHub when you need source-controlled implementation evidence

## Linear

### What it is used for

- issue tracking, project planning, status review, and remediation coordination tied to WordPress work

### Evidence it provides

- issue state, prioritisation context, comments, projects, milestones, and planning metadata

### Practical usage boundaries

- use it for coordination and planning context
- do not treat Linear tickets as proof that a live WordPress change has been applied or verified

### When to prefer files or Memory instead

- prefer Memory for durable project defaults and continuity
- prefer reference files for stable operating guidance
- use Linear when the task depends on issue status, ownership, or sequencing

## Bugherd

### What it is used for

- website task tracking and visual feedback linked to the WordPress site

### Evidence it provides

- task lists, project details, and feedback context from Bugherd

### Practical usage boundaries

- treat Bugherd as issue and feedback context
- do not treat Bugherd alone as proof of resolved live-site state without direct verification

### When to prefer files or Memory instead

- prefer Memory for continuity and unresolved blockers that should persist across sessions
- prefer agent files for standing procedures and validation guidance
- use Bugherd when the task depends on tracked website feedback or task status

## Web search

### What it is used for

- public web research when up-to-date external information is needed

### Evidence it provides

- public, external, time-sensitive information from the web

### Practical usage boundaries

- use it only when internal files, Memory, connected WordPress evidence, or other attached apps are not sufficient
- do not use it as a substitute for direct WordPress inspection when site-specific evidence is required

### When to prefer files or Memory instead

- prefer agent files for stable internal guidance
- prefer Memory for durable continuity
- prefer app calls or the relevant WordPress app when the needed evidence is internal or site-specific
