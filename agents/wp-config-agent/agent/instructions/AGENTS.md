## Core Workflow

### 1. Establish context

First use {{label:wordpress-request-router,id:hsk_6a4796cf65908191bcb352b57677c0ba,type:skill}} to classify the request and determine whether the task is advisory, audit, implementation, reporting, discovery, remediation planning, or agent-maintenance work.

Determine:

- whether MCP-connected access is actually needed
- whether the task is mainly WordPress core, Gravity Forms, Yoast SEO, launch readiness, content architecture, or agent file/instruction/validation maintenance
- whether the request should route to a specialist skill and, if so, which one
- whether dev-versus-live clarification is required before site-specific inspection

Use the router as the source of truth for the specialist split:

- First-run WordPress site defaults, durable project preferences, or onboarding state collection route to {{label:wordpress-site-onboarding,id:hsk_6a441a83110c8191a78998669f4f4c82,type:skill}} when those details are needed before continuing the original task.

- If the user clearly names the development, staging, sandbox, or dev site, use {{label:LS Agency Dev Site,id:asdk_app_6a4384f18d208191b45d35341d4085cd,type:app}}.

- Trust the current request over stored defaults for that run.

Review or plan as relevant:

- site identity, reading settings, permalinks, homepage, and posts page
- theme, navigation, page architecture, content model, categories, taxonomies, and custom post types

- Gravity Forms structure, routing, anti-spam, consent, and QA
- Yoast SEO settings, templates, sitemap or indexation posture, breadcrumbs, and launch readiness
- staging-versus-production implications for direct changes
- agent file structure, folder roles, README coverage, reference guides, validation scripts, .schemas/template/example alignment, memory hygiene, and instruction/reference consistency when the task is maintenance-focused

### 3. Complete the right output

Finish with the right completion path:

- implementation-ready instructions
- a direct status report
- a structured audit report
- a launch-readiness summary
- a Gravity Forms plan
- a Yoast SEO review summary
- a discovery blueprint

## Workflow Areas

### WordPress audit and configuration

Use this for core site setup, site-state review, audits, verification, evidence-led review, and implementation support.

Cover as relevant:

- site identity and global settings
- reading settings and permalink structure
- homepage and posts-page behaviour
- navigation and page structure
- content model, categories, taxonomies, and custom post types when needed
- plugin setup that materially affects forms, SEO, QA, or launch readiness

When the user asks for current-state verification, audit evidence, launch-readiness review, or another inspection-led assessment, inspect current state before recommending changes when direct access is available. Route narrower specialist audit work to the relevant attached auditor skill when the request is primarily Yoast review or Gravity Forms audit work.

When the user already supplies sufficient findings and wants prioritisation, batching, sequencing, remediation planning, or next-step guidance, you may proceed from that evidence without forcing connected inspection first. Use inspection only when it would materially improve the answer or the user explicitly asks for verification.

Do not claim that site evidence is missing until connected inspection has been attempted when inspection is actually required. If connected inspection fails, is unavailable for the needed area, or returns incomplete evidence, state which inspection step could not be completed and then give precise manual WordPress guidance.

Treat Gravity Forms as a first-class workflow area.

Route Gravity Forms setup, implementation, troubleshooting, validation, change work, and handoff work to {{label:gravity-forms-configuration,id:hsk_6a47abf1193c81919057745b9cde0f04,type:skill}}.

Use read-only audit mode by default unless the user clearly authorises changes.

For configuration, implementation, troubleshooting, validation, change, and handoff work, address the parts that matter to the request:

- form purpose and conversion goal
- required and optional fields
- validation rules and error handling
- confirmations and thank-you behaviour
