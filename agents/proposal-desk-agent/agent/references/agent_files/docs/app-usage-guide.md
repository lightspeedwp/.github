## Purpose

This guide tells Proposal Desk which source or attached app to use once the workflow is known.

Use `skill-directory/skill-routing-guide.md` for skill choice and handoffs. Use this file for source priority, per-app use, and permission guardrails.

## Source priority

1. Current request artefact and attachments
2. business-context.md
3. docs and reference control files
4. Attached reference files
5. Memory
6. Google Drive
7. Gmail
8. Linear
9. GitHub
10. Asana
11. Google Calendar
12. Figma
13. Google Contacts
14. Slack
15. Web search

Use the lowest-cost grounded source that can complete the task well.

Use Memory for reusable defaults and prior confirmed context, not as the primary evidence source for proposal claims.

## Core operating posture

- Start with files, attached artefacts, and grounded context before apps.
- Prefer read actions before write actions.
- Prefer the narrowest app that can answer the question or complete the job.
- Separate evidence gathering from execution when a tool supports both.
- Treat create, update, delete, send, forward, post, comment, merge, rerun, respond, import, and file-writing actions as consequential.
- If the user did not ask for a side effect, prefer a draft, review note, recommendation, or proposed next step instead of executing the change.

## Per-app usage

### Google Drive

Use Google Drive for:

- approved proposal wording
- reusable proof points
- working documents or templates
- document retrieval, export, or structured source material
- document creation or updates after the draft is grounded

Prefer Google Drive over Slack when the need is formal source material, reusable wording, or maintained working documents.

### Gmail

Use Gmail for:

- inbox search for past customer, partner, or internal threads
- message history that clarifies decisions or commitments
- attachment reading from relevant email threads
- draft or send workflows only when email execution is part of the requested outcome

Do not use Gmail by default when files, Drive, or the current artefact already provide the needed evidence.

### Linear

Use Linear for:

- issue, project, initiative, milestone, customer, or documentation context
- tracked product planning evidence
- status history or known implementation constraints
- structured delivery context for proposal accuracy

Prefer Linear over Slack for tracked product and delivery context.

### GitHub

Use GitHub for:

- repository, issue, pull request, workflow, or commit context
- technical evidence from code, diffs, reviews, or repo structure
- delivery-risk or packaging evidence tied to actual technical artefacts
- WordPress plugin packaging review evidence from repositories or release history

Prefer GitHub over Slack when technical evidence is needed.

### Asana

Use Asana for:

- project or task status context
- owner and workflow context from tracked operational work
- portfolio or team context for delivery planning
- task creation or updates only when operational execution is part of the requested outcome

### Google Calendar

Use Google Calendar for:

- event lookup
- availability checking
- schedule context that materially affects coordination or planning
- event creation or updates only when calendar execution is explicitly requested

Do not use Calendar as a generic source of project truth.

### Figma

Use Figma for:

- design screenshots or design context
- metadata, libraries, diagrams, decks, or code-connect context
- structured visual evidence that improves design, UX, or briefing work
- file creation workflows only when the output explicitly needs a Figma-side artefact

### Google Contacts

Use Google Contacts for:

- contact lookup
- contact verification
- checking saved people or organisation details relevant to the current task

Treat it as a retrieval tool for this agent, not a messaging or update tool.

### Slack

Use Slack for:

- internal discussion context
- likely owners for open gaps
- blocker, decision, or review history
- thread context that explains why a decision was made

Do not treat Slack as primary evidence for proposal claims unless the user explicitly wants internal-context review or no stronger source exists.

Do not use Slack as the default outbound channel.

### Web search

Use Web search for:

- current public information not available in files, Memory, or attached apps
- external verification of public facts
- up-to-date market, vendor, or public-source context

Use it only when stronger internal or attached sources do not already answer the question.

## Permission guardrails by app

### Read-first posture

Default to retrieval, review, comparison, and evidence gathering before using any write-capable action.

### Write-capable apps

These attached apps have write-capable actions and should be used carefully:

- Google Drive
- Gmail
- Linear
- Google Calendar
- GitHub
- Asana
- Figma

For these apps:

- use writes only when the task clearly calls for that outcome
- keep changes minimal and tightly scoped
- avoid speculative extras
- prefer reversible or draft-like changes where possible

### Retrieval-first apps

Treat these attached apps as retrieval-first for this agent:

- Slack
- Google Contacts

Do not use them for outbound or state-changing actions unless the task explicitly requires it.

## Light skill-to-app routing

- Use `proposal-intake` before app lookups when the request is a new RFP, questionnaire, proposal brief, or diligence pack.
- Use `proposal-defaults-onboarding` before app lookups when reusable evidence, routing, or intake defaults are missing.
- Use `evidence-claims-check` before or alongside Google Drive, Gmail, GitHub, Linear, or Slack retrieval when the task is to verify claims or classify support strength.
- Use `rfp-response` after intake when the task is to produce draft proposal content or a first-pass response pack.
- Use `wordpress-plugin-packaging-review` when plugin assessment is the primary task and repository, vendor, pricing, or operational evidence matters.
- Use `markdown-format-validator` at the end of substantial Markdown deliverables.

## Routing rules

- Start with files and current artefacts before apps.
- Use Google Drive for reusable working material and approved source wording.
- Use Gmail for thread-based context or attachment evidence when email history matters.
- Use Linear, GitHub, and Asana for tracked product, technical, and operational context.
- Use Google Calendar only when availability or event state matters.
- Use Figma for design and visual-context retrieval.
- Use Google Contacts only for contact verification.
- Use Slack for internal context and owner routing after stronger formal sources have been checked.
- Use Memory for reusable working defaults only.
- Use Web search only when attached and connected internal sources do not already provide enough evidence.
- If both Google Drive and Slack could help, prefer Google Drive for reusable wording and source material, then use Slack only to fill ownership, history, or blocker context gaps.
- If both GitHub and Slack could help with technical questions, prefer GitHub for factual implementation evidence and Slack only for discussion context.
- If both Linear and Slack could help with delivery questions, prefer Linear for tracked status and Slack only for informal background or owner context.

## What not to do

- Do not invent permissions that are not explicitly available through attached tools.
- Do not claim broad admin authority across Slack, Google Workspace, GitHub, Asana, Linear, Figma, calendars, email, or contacts.
- Do not use write-capable apps to make changes just because they are available.
- Do not send emails, update docs, create calendar events, open issues, create tasks, edit repo files, or generate design artefacts as speculative extras.
- Do not overwrite or materially alter shared records unless the task clearly requires it.
- Do not retrieve more sensitive internal material than the current task needs.
- Do not use internal discussion, Memory, or prior draft language as final proof when stronger evidence is available.
