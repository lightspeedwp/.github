Use questionnaire files as selective intake resources, not mandatory forms.

## Default handling rules

1. Start with the user goal and active workflow.
2. Choose one best-fit questionnaire source first.
3. Combine sources only when the workflow clearly spans multiple domains.
4. Ignore unrelated questionnaires.
5. If intent is unclear, ask: “What was this questionnaire intended to help capture for this workflow?”
6. Continue with a safe default instead of stalling.

## Best-fit defaults

- `website-briefing-questionnaire.md`
  - Best for broad website discovery, scope framing, stakeholders, goals, technical context, and initial project qualification.
- `website-design-questionnaire.md`
  - Best for visual direction, UX expectations, layout preferences, inspiration, and design cues.
- `design-briefing-questionnaire.md`
  - Best for design processes, approvals, brand expression, assets, and review ownership.
- `website-content-collection-questionnaire.md`
  - Best for website content readiness, page-level content needs, source-asset gaps, and content approvals.
- `content-collection-questionnaire.md`
  - Best for content gathering, editorial inputs, asset collection, and page-by-page content support.
- `tone-of-voice-questionnaire.md`
  - Best for messaging, voice, brand personality, tone constraints, and content-style defaults.
- `ecommerce-briefing-form.md`
  - Best for catalogue, checkout, payments, fulfilment, integrations, legal, tax, shipping, and launch-readiness intake.
- `standard-website-package-questionnaire.md`
  - Best for standard website package fit, scope boundaries, assumptions, and qualification checks.
- `tour-operator-website-planning-checklists.md`
  - Best for tour-operator planning, destinations, itineraries, launch-readiness, operational checklist coverage, and handoff controls.
- `tour-operator-blog-questionnaire.md`
  - Best for tour-operator blog strategy, destinations, SEO support, editorial planning, and content workflow discovery.

### Governance, chatbot, or approval-heavy workflows

Use only the sections that help clarify:

- audience
- approved sources
- exclusions
- privacy or legal requirements
- claims
- review ownership
- escalation or support routes

## Ignore rules

Ignore a questionnaire when:

- it covers a different project type than the current task
- it would add noise instead of resolving blockers
- its defaults are weaker than evidence from the current request
- it duplicates fields already captured from better-fit sources
- it implies capabilities or commitments outside the current workflow
