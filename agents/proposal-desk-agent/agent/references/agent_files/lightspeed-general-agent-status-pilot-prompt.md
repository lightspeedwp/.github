Use this prompt when you want the agent to assess its current readiness, run a controlled pilot-planning workflow step by step, and leave behind a clean checkpoint so the work can be resumed later without starting over.

## Trigger prompt

```markdown
Run the LightSpeed agent status and pilot rollout plan for this agent.

Complete the plan step by step.
Keep Verified, Inferred, and Owner must confirm clearly separated.
Use only settings, files, tools, and rollout facts that are visible in the current context or explicitly checked during this run.
If prior work already exists, resume from the first incomplete step instead of restarting.
Finish by giving the final rollout recommendation and a progress snapshot that makes the plan easy to resume after a break.
```

## Resume prompt

```markdown
Resume the LightSpeed agent status and pilot rollout plan from the first incomplete step.

Reuse the verified findings and completed sections already established.
Update anything that changed because of new evidence.
Do not restart completed work unless accuracy requires it.
Finish the remaining steps, restate any owner confirmations still needed, and end with an updated progress snapshot.
```

## Progress snapshot rule

If the plan may need to continue later, end with this section so a user can paste it back in with the resume prompt:

```markdown
## Plan progress snapshot
- Last completed step: [step number and name]
- Remaining steps: [step numbers and names]
- Verified so far: [short bullets]
- Owner confirmations still needed: [short bullets]
- Current rollout recommendation: [current best recommendation]
```

## Core rules

- Do not pretend you can inspect hidden settings, sharing, teammate access, publishing, app readiness for other users, Slack deployment, schedules, or permissions unless they are visible in the current context or explicitly checked during the run.
- Separate everything into:
  - Verified
  - Inferred
  - Owner must confirm
- Prefer current editor-visible facts over assumptions or older file guidance.
- If a detail comes from an attached file, treat it as verified only if you explicitly checked that file during the current run.
- Use practical defaults when information is missing.
- Ask at most one focused clarifying question only if a blocker prevents a sensible pilot recommendation.
- Default to a small internal pilot and read-only behaviour unless explicit approval says otherwise.
- Do not recommend wider rollout until testing, access expectations, and approval boundaries are clear.

## Approved vs excluded materials policy

Use this short policy during the pilot:

**Approved by default**

- low-risk internal examples
- sanitised client examples
- approved briefs, questionnaires, and discovery notes
- non-sensitive real work needed for proposal and review testing

**Excluded unless Ash explicitly approves them for pilot use**

- live client proposals with confidential pricing or commercial terms
- NDA-bound or client-confidential documents
- security questionnaires with sensitive controls, architecture, or vendor details
- private internal strategy, finance, legal, or people documents
- personal data or privacy-sensitive records
- unapproved claims decks or drafts that could be repeated as fact

If uncertain, treat the material as excluded and ask for owner confirmation.

## Step-by-step plan

### Step 1. Capture visible agent status

Identify the current visible facts first.

Check for:

- mission and intended workflow
- instruction quality and boundaries
- attached files and test materials
- attached apps and approval posture
- Memory state
- Slack deployment state
- schedule state
- live versus draft state when visible

Output:

- a short list of verified status facts
- a short list of obvious gaps or unknowns

### Step 2. Classify readiness by area

Assess these areas conservatively:

- Mission clarity
- Instructions
- Knowledge files
- Tools/connectors
- Memory behaviour
- Team sharing
- Slack/channel deployment
- Scheduled tasks
- Test materials
- Human approval gates

For each area, label:

- Status: Ready / Needs work / Unknown
- Evidence level: Verified / Inferred / Owner must confirm
- Notes
- Action needed

### Step 3. State what is ready now

List only what can be used safely right now.

Be conservative.
Do not imply full rollout readiness unless the evidence supports it.

### Step 4. Identify owner-confirmation items

List only the items Ash or the owner must confirm manually.

Typical examples:

- sharing model
- teammate access
- whether the latest live version is the intended one, when not directly visible
- whether each teammate needs their own app connections
- whether Memory behaviour is intended for team use
- whether any writes are allowed during the pilot
- whether any sensitive or client-facing sources need extra restrictions

### Step 5. Build the pilot model

Recommend a controlled pilot with:

- 3 to 5 testers
- 1 to 2 weeks
- real but low-risk tasks
- read-only behaviour unless approved otherwise
- one shared feedback tracker

Include:

- who should test
- what each tester should try
- what inputs or evidence they should provide
- what success looks like

### Step 6. Write onboarding instructions for testers

Write short instructions Ash can send to teammates.

Include:

- what the agent is for
- what testers should paste into the agent
- what files or links they should provide
- how to judge whether the output is good
- what not to use it for during the pilot
- how to log feedback

### Step 7. Generate realistic tester prompts

Provide 8 to 12 realistic prompts.

For each prompt include:

- Prompt text
- Best input type
- What the tester should check
- Pass/fail guidance

### Step 8. Create compact pilot test cases

Create a compact test-case table with these columns:

- Test ID
- Tester role
- Scenario
- Prompt to test
- Inputs required
- Expected behaviour
- Pass criteria
- Risk area
- Notes

### Step 9. Add guardrails and escalation rules

State the practical guardrails clearly.

Include:

- no sending, publishing, updating, deleting, ticket creation, task updates, or client contact without explicit approval
- escalate when source evidence is missing, contradictory, stale, sensitive, privacy-related, legal, pricing-related, security-related, or otherwise risky
- label assumptions clearly
- prefer a smaller verified answer over a confident unsupported answer

### Step 10. Recommend improvements and final rollout status

Group improvements into:

- Must fix before pilot
- Should improve during pilot
- Later enhancements

Then choose one final recommendation:

- Ready for owner testing
- Ready for small team pilot
- Needs hardening before pilot
- Not ready for team use

Explain the decision in 3 to 5 bullets.
