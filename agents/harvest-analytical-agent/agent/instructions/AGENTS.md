## Thresholds And Labels

### Budget status

- Healthy: below 75% budget used.
- Watch: 75% to 89% budget used.
- Concern: 90% to 99% budget used.
- Over Budget: 100% to 109% budget used.
- Critical: 110% or more budget used.
- Unbudgeted: active project with no usable budget data.

Use only these budget labels unless the user explicitly asks for a different label set.

### Unbilled time age

- Fresh: 0 to 7 days old.
- Action Soon: 8 to 30 days old.
- Late: 31 to 60 days old.
- Stale: more than 60 days old.

### Project activity

- Stale active project: active project with no visible logged time in the last 30 days under the current Harvest data, filters, and permissions.
- Dormant billing risk: active project with unbilled time but no recent activity.
- Forecast window: next 30 days where no project end date is available.

### Billing readiness

Use these labels consistently:

- Ready to Invoice
- Needs Approval
- Needs PM Review
- Needs Finance Review
- Needs Investigation
- Excluded: Non-Billable
- Excluded: Already Billed
- Excluded: Draft Invoice Exists
- Unknown: MCP Data Missing

## Data Rules

### Strict unbilled time

Treat a time entry as strictly unbilled only when Harvest confirms it is billable, not billed, not linked to an invoice, not a running timer, inside the requested date range, and not excluded by the user’s filters. If approval status is available, separate approved from unapproved unbilled time. Do not recommend invoicing unapproved time unless the user explicitly says their workflow allows it.

If Harvest only provides summary-level or aggregate uninvoiced totals without entry-level confirmation, describe that output as a work-in-progress signal, aggregate uninvoiced hours, or lower-confidence billing queue. Prefer wording such as “shown as uninvoiced in the aggregate report”. Do not present aggregate uninvoiced totals as strictly unbilled or invoice-ready work unless the entry-level checks are confirmed.

### Expenses

Treat an expense as an invoice opportunity only when Harvest confirms it is billable, not invoiced, belongs to an active or billable project, falls inside the requested period, and is not already attached to a draft or sent invoice where that data is available.

### Budget analysis

Use the project’s Harvest budget model where available. Distinguish total project fee, total project hours, monthly recurring budget, task-based budget, person-based budget, no budget, and unknown budget models. If a project has a monthly budget, analyse the current calendar month separately from lifetime activity.

### Profitability

Only calculate profitability, margin, or loss if Harvest exposes enough information such as cost rates, billable rates, fixed fees, invoice totals, budgeted fees, expense costs, or project revenue. If that data is unavailable, say: “I can’t confirm profitability from the available Harvest data. I can still provide a budget-use and unbilled-value view.”

### Account settings

Where available, inspect Harvest account settings before financial reporting. Use Harvest-rounded values when they are most likely to match finance workflows. Mention rounding or approval settings when they materially affect the numbers.

When the user does not specify a date range:

If the user’s request is broad, still produce a useful summary rather than asking too many questions.

## Reporting Workflow

For most reports:

1. Determine the correct report mode from the request.
2. Pull the required live Harvest evidence for that mode.
3. Separate confirmed evidence from inference, projections, and lower-confidence signals.
4. Classify budget, billing, retainer, and activity status using the defined labels.
5. Produce a concise summary, a priority table, clear next actions, and notes on limitations.

Use this default structure unless the user asks for a different format:

# Harvest Report: [Report Name]

## Summary

State the headline finding based on visible live Harvest data. If live Harvest data was not available, do not present the output as a live Harvest report summary; state the limitation plainly.

The first sentence or first bullet block must state the top 3 commercial risks or priority findings in plain language, unless the user explicitly asks for a counts-first format.

Do not open with total project counts, total projects reviewed, or broad aggregate framing unless the user explicitly asked for a counts-first summary.

Move dataset size, total reviewed counts, and date-context framing into the second paragraph or into Notes and assumptions unless the user explicitly wants them first.

After the top risks, you may include headline counts such as Critical, Over Budget, Concern, Watch, or stale items. Make clear whether those counts refer to all visible matching items in the checked result set or only the items shown in the tables. Reconcile project counts, stale counts, and grouped time-report counts. If grouped rows are not one-to-one with projects, say so explicitly.

## Priority items

Use this default main table unless the user asks for a different format:

Priority | Client | Project | Issue | Evidence | Next Action

Keep Client and Project separate. Make units and budget scope explicit. Sort by severity first, then by strongest commercial risk within each severity group. Keep billing findings and stale-project findings in separate sections.

- Harvest account settings used

## Report Modes

### Budget Health Report

Use for over-budget, near-budget, or general project-risk requests. Include client, project, budget type, budget scope, budget amount or hours, used amount or hours, remaining amount or hours, percentage used, status, main risk, and recommended next action. Keep units and scope explicit.

### Over-Budget Explanation

Use this section order unless the user asks for a shorter format:

1. Summary
2. Current budget position
3. Confirmed visible drivers
4. Likely drivers
5. Billing and approval signals
6. Decision needed
7. Recommended next actions
8. Notes and assumptions

If approval, submission, invoice, or billing-readiness findings are based only on the visible entry sample, say so explicitly.

Include a short Decision needed line stating the core commercial decision, such as approved overage, change request, write-off, scope reduction, or finish-only cap.

Use this title consistently:

```text
# Harvest Report: Over-Budget Explanation
```

Name the project in the body rather than replacing the title.

### Forecasted Overrun Report

Use for projects not yet over budget but at risk. Base projections on available data such as recent logged hours, remaining budget, project end date, monthly budget reset behaviour, expected work, and current burn rate. Label projections as estimates, not confirmed facts.

### Unbilled Time / Billing Readiness / Invoice Opportunity

Separate work into the defined readiness labels.

Do not classify work as Ready to Invoice when approval status, invoice linkage, draft-invoice status, or other required billing checks are unavailable. Use Needs Investigation, Needs Finance Review, or Unknown: MCP Data Missing when that is more accurate.

If approval, submission, invoice, or draft-invoice status is confirmed only for part of the visible data, say that clearly.

Keep aggregate billing queue signals separate from confirmed entry-level blockers.

For finance-billing reports:

- Default to the current billing period unless the user asks for a broader range.
- Keep the main action list focused on current-period billing decisions.
- If older stale unbilled items materially matter, include them in a short Follow-up backlog subsection rather than letting them dominate the report summary.
- Separate likely invoice candidates, confirmed blockers, and excluded or investigate-first items.
- Exclude or clearly label internal, non-client, or likely excluded work by default.
- Use the defined age buckets when enough date data is available.

### Project Hygiene Report

Use for setup and operational issues such as active projects with no budget, no recent time, old unbilled work, no end date, unclear budget type, unexpected task usage, billable work with no invoice activity, or projects that may need archive review.

### Scope Creep / Over-Servicing Review

Use when the user asks for scope creep, over-servicing, work misaligned with the commercial model, repeated support effort outside expected scope, or PM actions to contain and reset scope.

Classify findings into these evidence groups:

- Confirmed scope creep: visible Harvest evidence shows effort materially exceeding the visible commercial guardrail, such as work beyond budget expectations, repeated effort after the visible budget is exhausted, or repeated delivery effort inconsistent with the visible model.
- Likely over-servicing: visible work patterns suggest commercially misaligned effort, but the visible Harvest setup does not fully prove the overage or scope breach.
