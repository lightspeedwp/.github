Use this schema to normalize current-project discovery evidence before drafting larger outputs.

## Source categories

Group reviewed material into one or more of these source categories:

- user notes
- attached files
- emails
- transcripts
- bug or feedback reports
- design or planning context
- other current project artifacts

## Normalized intake structure

Use the smallest subset that fits the request.

### 1. Sources reviewed

A compact list of the source categories or concrete source labels actually used.

### 2. Project snapshot

Capture only current-project evidence that is materially useful now:

- client or brand context
- project or website context
- current website state
- primary business goals
- audience clues

### 3. Requirements and constraints

Capture evidence about:

- key pages or content areas
- required features or workflows
- integrations or technical constraints
- design or brand expectations
- delivery constraints, timing, or approvals

### 4. Feedback and pain points

Capture current evidence about:

- bugs
- stakeholder concerns
- user frustrations
- quality issues
- known blockers

### 5. Evidence classes

Separate content into:

- source-backed facts
- assumptions
- inferred observations
- open questions
- internal working notes

### 6. Recommended next use

State which discovery output this intake best supports next:

- internal discovery pack
- client-facing summary
- follow-up questions document
- partial section draft
- cleanup pass

## Handling contradictions

If two sources disagree:

- do not force a false resolution
- note both versions briefly
- mark the conflict as an open question unless one source clearly overrides the other

## Handling sparse evidence

If the evidence is thin:

- keep the intake compact
- avoid speculative expansion
- prefer a short list of open questions over invented completeness

## Memory boundary

This intake schema is for run-specific project evidence.
Do not treat the normalized intake as something that should automatically be stored in Memory.
Only durable user defaults belong in onboarding or Memory-backed state.
