Use these examples when the request is ambiguous, connector access is incomplete, or the brief risks overclaiming. They are anonymised patterns, not real customer records.

## Example 1: Zendesk-only support pulse

### User request

`Use zendesk-customer-research for Example Travel over the last 7 days before I reply.`

### Normalised input

- customer_name: Example Travel
- resolved_window: 2026-06-18 -> 2026-06-25
- research_mode: support pulse
- primary_question: what should support know before the next reply?
- available_sources: Zendesk
- unavailable_sources: Gmail, Slack, Drive not checked because Zendesk was sufficient for the requested pulse

### Evidence pattern

- Zendesk has two recent tickets: one resolved login question and one open low-severity content-import question.
- No high-severity or incident ticket appears in the checked window.
- Ownership is clear on the open ticket.

### Good synthesis pattern

`Current support state: Watch (Confidence: Medium)`

`So what: support can reply normally, but should acknowledge the open content-import question and avoid saying the account is fully stable until the open ticket is resolved. [Z2]`

### Ledger pattern

- `[Z1] Zendesk search: organisation:"Example Travel" 2026-06-18..2026-06-25 - relevant - resolved login question; supports Recent Zendesk activity and Weekly view`
- `[Z2] Zendesk ticket #12345 - relevant - open low-severity content-import question; supports Current support state, Open risks, Recommended reply context`
- `[E1] Gmail - not checked - not needed for a Zendesk-only support pulse`
- `[S1] Slack - not checked - not needed for a Zendesk-only support pulse`

### Why this is good

The brief does not call the customer `Stable` just because severe tickets were absent. It keeps the open ticket visible and explains why confidence is not High.

## Example 2: Zendesk unavailable, pasted ticket export supplied

### User request

`I do not have Zendesk connected in this shared agent, but here is a pasted export for Example Retail. Give me a support-health brief.`

### Normalised input

- customer_name: Example Retail
- resolved_window: based on pasted export dates only
- research_mode: support pulse
- primary_question: what does the pasted Zendesk evidence suggest?
- available_sources: pasted Zendesk export
- unavailable_sources: live Zendesk connector
- confidence_starting_point: Low until live Zendesk status is verified

### Evidence pattern

- Pasted export includes three tickets from the last 10 days.
- One ticket appears open in the export, but the current live status cannot be checked.
- Export has no internal notes or SLA fields.

### Good synthesis pattern

`Current support state: Unknown (Confidence: Low)`

`So what: the pasted export suggests repeated checkout friction, but live Zendesk access is unavailable, so support should verify current ticket status before promising resolution or escalation status. [O1]`

### Ledger pattern

- `[Z1] Live Zendesk - unavailable - connector not available to this shared agent; current ticket status, owner, SLA, and internal notes could not be verified`
- `[O1] Pasted Zendesk export from user - relevant - includes three recent checkout-related tickets; supports Current support state, Key themes, Open risks`
- `[E1] Gmail - not checked - not requested and not needed to interpret pasted ticket export`

### Required wording

Use:

- `Live Zendesk access was unavailable to this agent.`
- `The pasted export suggests...`
- `Current status should be verified before replying.`

Avoid:

- `Zendesk shows no other issues.`
- `The ticket is still open.` unless the export timestamp is clearly current.
- `Support health is Stable.`

### Why this is good

It treats the export as useful but narrower than live Zendesk. It does not convert missing connector access into a no-result search.

## Example 3: Prior commitments across Zendesk and email

### User request

`Check prior support commitments for Example Publishing before I send the next update.`

### Normalised input

- customer_name: Example Publishing
- research_mode: prior commitments
- resolved_window: last 30 days unless the user gave a narrower window
- primary_question: what has LightSpeed already promised or implied?
- intended_sources: Zendesk first, then Gmail if support commitments may have happened by email

### Evidence pattern

- Zendesk contains a public reply promising an update after developer review.
- Gmail contains a later account email mentioning a target date, but no delivery confirmation.
- Slack mentions a possible fix, but it was informal and not customer-facing.

### Good synthesis pattern

`Recommended reply context:`

- `Acknowledge: LightSpeed previously said the item would be reviewed by a developer, and a later email mentioned a target date. [Z1][E1]`
- `Avoid: do not say the fix was confirmed; Slack only shows informal internal discussion, not a customer-facing commitment. [S1]`
- `Team next step: verify implementation status before giving a new date. [P1]`

### Ledger pattern

- `[Z1] Zendesk ticket #23456 - relevant - public reply promised developer review; supports Recommended reply context`
- `[E1] Gmail thread with Example Publishing - relevant - target date mentioned; supports Recommended reply context and Open risks`
- `[S1] Slack search - relevant - informal fix discussion only; supports Avoid wording`
- `[P1] GitHub/Linear/Asana implementation status - unavailable or not checked - status still needs verification before replying`

### Why this is good

It separates customer-facing commitments from internal discussion and prevents the next reply from overstating delivery status.

## Example 4: No reliable evidence found

### User request

`Give me a quick support pulse for Example Events.`

### Normalised input

- customer_name: Example Events
- research_mode: support pulse
- resolved_window: last 7 days
- primary_question: current support context

### Evidence pattern

- Zendesk search returns no relevant results for the organisation and domain.
- Gmail and Slack are unavailable in the shared agent.
- No pasted support thread was provided.

### Good synthesis pattern

`Current support state: Unknown (Confidence: Low)`

`So what: no relevant Zendesk results were found in the checked window, but supporting sources were unavailable and no pasted thread was supplied, so this should not be treated as a positive health signal. [Z1][E1][S1]`

### Ledger pattern

- `[Z1] Zendesk organisation/domain search - no result - no relevant tickets found in the checked 7-day window`
- `[E1] Gmail - unavailable - connector not available to this shared agent`
- `[S1] Slack - unavailable - connector not available to this shared agent`

### Why this is good

It avoids the common failure mode of calling an account `Stable` because nothing was found.
