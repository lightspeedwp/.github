Use this reference when installing or QA-checking the skill in a shared workspace agent, or when the available Zendesk connector actions differ between agents.

The profile is not a credential store and is not required for every report. It is a portable description of what the active shared agent can read, which filters are safe to use, and which Zendesk fields are visible. It helps the agent avoid user-specific assumptions while still producing useful backlog analysis.

## When to use

Use a capability profile when:

- the skill is being added to a new shared agent
- reports behave differently for different teammates
- SLA, CSAT, brand, group, custom fields, or Help Centre access is uncertain
- the agent needs to explain why a report is limited
- the team wants a repeatable smoke test before rollout

Do not use a capability profile to store:

- personal Zendesk views
- credentials, tokens, or private URLs
- customer-sensitive ticket contents
- one-off ticket counts or temporary backlog state
- unconfirmed assumptions about queue ownership

## Minimal profile fields

A useful profile should answer these questions:

1. Can the agent count tickets?
2. Can the agent search ticket metadata?
3. Can it filter by date, status, priority, assignee, group, brand, organisation, tag, form, channel, and text?
4. Can it read ticket conversations when a key claim requires confirmation?
5. Can it see SLA data?
6. Can it see CSAT or satisfaction data?
7. Can it search or read Help Centre articles?
8. Which Zendesk fields are unavailable or unreliable?
9. Which actions must remain read-only unless the user explicitly asks for writes?

## Recommended profile format

Use `schemas/workspace-capability-profile.schema.json` as the validation contract and `profiles/workspace-capability-profile-example.json` as an anonymised example.

Keep field identifiers generic unless a field has been confirmed in the active shared agent. Prefer names like `customer_impact`, `product_area`, or `blocked_reason` over raw custom-field IDs.

## Using a profile during reporting

Before producing a report:

1. Match the user request to the profile capabilities.
2. Use available read actions first.
3. State unavailable evidence clearly instead of filling gaps with assumptions.
4. Downgrade confidence when comparison windows, SLA, CSAT, or ticket details are unavailable.
5. Keep recommended actions support-owned and within visible evidence.

## Permission-limited response pattern

When the profile shows that the agent cannot access enough Zendesk evidence, use wording like:

> I cannot produce an evidence-backed backlog report in this shared agent environment because ticket counts and ticket search metadata are not available. I can still provide a report structure or a capability checklist, but I should not invent backlog numbers, SLA status, owners, trends, or ticket examples.

## Shared-agent maintenance

Review the profile when:

- Zendesk connector permissions change
- new ticket fields become available
- SLA or CSAT visibility changes
- the skill is copied to another shared agent
- the team adds or removes Zendesk groups, brands, or forms

Treat the profile as operational configuration, not memory. If it becomes outdated, prefer saying capability is uncertain and rerun the capability preflight.
