Use this reference when the escalation skill risks acting like a network-wide Zendesk router. The `zendesk-router-skill` owns the full Zendesk skill network. This specialist skill should know only its own boundaries, common handoffs, and when to return to the router.

## Specialist boundary

`zendesk-customer-escalation` owns one deliverable: a Zendesk-first escalation brief for a support case that needs cross-functional attention, urgency handling, risk ownership, or a clear decision from another team.

Stay inside this skill when the user needs:

- an escalation brief for Engineering, Product, Security, Leadership, or senior Support specialist review
- severity and urgency wording for a case that appears escalation-worthy
- an evidence-backed internal escalation ask
- escalation-ready customer impact, risk, attempted steps, evidence gaps, and next checkpoint notes
- QA of the escalation shape only when the current draft is already within this skill's scope

Do not use this skill as a general router for every Zendesk, support, customer, duplicate, knowledge, backlog, or reporting request.

## Common direct handoffs

Use only these common handoffs from inside this skill:

| Handoff | Use when |
| --- | --- |
| `zendesk-evidence-collector` | Case evidence is weak, incomplete, not Zendesk-grounded, or root-cause/diagnostic facts are missing before escalation. |
| `zendesk-case-readiness-check` | It is unclear whether the case has enough evidence for escalation, reply drafting, handoff, or another concrete deliverable. |
| `zendesk-handoff-prep` | The case needs routine internal transfer, continuity notes, specialist review, or ownership handoff without escalation-level risk. |
| `zendesk-draft-response` | The customer needs an interim update, apology, limitation explanation, expectation-setting reply, translation, or follow-up alongside the internal escalation. |
| `zendesk-customer-research` | Broader customer/account support history, prior commitments, relationship risk, or recent activity is needed before escalation. |
| `zendesk-evidence-quality-review` | A drafted escalation brief needs evidence QA, risk-wording review, or unsupported-claim cleanup before sharing. |

Do not add new specialist handoffs here unless they are common, stable, and directly adjacent to escalation work. Keep rare or uncertain routing in `zendesk-router-skill`.

## Return to the router

Return to `zendesk-router-skill` instead of choosing a specialist when:

- the user asks which Zendesk skill, workflow, or next step should handle a request
- the request spans multiple possible specialist outputs and the primary deliverable is unclear
- the best route may involve duplicate review, pattern review, knowledge creation, backlog/trend reporting, broad triage, customer research, escalation, handoff, or reply drafting and no single adjacent handoff is obvious
- the task starts from a vague customer/account/issue summary without a clear escalation outcome
- the user asks for a combined workflow plan across the Zendesk skill network
- the request depends on network-wide policy, skill naming, ownership, sequencing, or orchestration
- the case appears outside escalation scope and no common direct handoff clearly applies

When returning to the router, provide a short reason and the clearest known facts. Do not perform a full triage or maintain a list of all available Zendesk skills inside this specialist skill.

## Routing response shape

When this skill should not continue, keep the response compact:

```markdown
This looks outside `zendesk-customer-escalation` because [reason]. Return to `zendesk-router-skill` with: [known ticket/customer/issue/context].
```

If one adjacent handoff is clearly enough, use that handoff directly and explain why. If two or more non-adjacent routes are plausible, return to the router.

## Anti-patterns

Avoid:

- listing or maintaining the full Zendesk skill network inside this skill
- choosing between many unrelated Zendesk specialist skills from inside this skill
- adding broad routing tables for duplicate, knowledge, backlog, trend, triage, or support-reporting workflows
- treating every unclear support request as an escalation
- combining escalation, customer reply, knowledge draft, backlog report, and duplicate review into one specialist output
- relying on personal memory or author-specific connector access to decide routing
