Use these examples only as classification calibration. They are synthetic and must not be treated as real Zendesk evidence, customer history, incident records, or source-of-truth data.

When a live case resembles one of these examples, still prioritise the actual Zendesk evidence and supplied ticket details. Use the examples to sharpen the distinction between duplicate, related, repeated pain, broader incident, and inconclusive classifications.

## Example 1: Likely duplicate

### Input pattern

- Ticket ZD-10001: Organisation A reports that the checkout confirmation email is not sent after a successful card payment on Site A.
- Ticket ZD-10002: Same requester from Organisation A opens a second ticket 20 minutes later with the same order number, same payment method, same site, and same missing confirmation email.
- Internal note on ZD-10001 says support already reproduced the issue and is preparing a reply.
- No unique customer impact is present in ZD-10002 beyond the repeated report.

### Classification

- Relationship classification: likely duplicate
- Confidence: high

### Why

The tickets describe the same symptom, same customer, same site, same workflow, same order context, and likely same resolution path. Handling them separately would create redundant support work.

### Support handling

- Link tickets: yes
- Merge tickets: yes, if Zendesk policy allows and any useful detail from ZD-10002 is preserved first
- Keep separate: no
- Escalate: not yet
- Next workflow: none, unless the merged case needs deeper investigation

## Example 2: Related but distinct

### Input pattern

- Ticket ZD-10011: Organisation B reports that the checkout address validation rejects valid postal codes for customers in Country X.
- Ticket ZD-10012: Organisation B reports that shipping rates are missing for some rural areas in Country X.
- Both mention checkout failure and Country X.
- Metadata shows different plugins/integrations involved: address validation versus shipping-rate lookup.
- Customers are affected at different checkout steps.

### Classification

- Relationship classification: related but distinct
- Confidence: medium

### Why

The tickets share customer, country, and checkout area, but the symptoms and likely causes differ. Merging would risk losing separate investigation paths.

### Support handling

- Link tickets: yes, as related checkout issues
- Merge tickets: no
- Keep separate: yes
- Escalate: not yet, unless either case has high impact or blocked revenue
- Next workflow: zendesk-evidence-collector if root cause proof is needed

## Example 3: Repeated pain pattern

### Input pattern

- Ticket ZD-10021: Customer asks how to add an advert placement to an article page.
- Ticket ZD-10022: Different customer asks why sponsored placements do not appear in the expected sidebar.
- Ticket ZD-10023: Another customer asks which ad slot name to use for campaign booking.
- The tickets occur over several weeks.
- No shared defect, outage, or failed deployment is evident.
- Public replies show support repeatedly explaining the same setup concepts.

### Classification

- Relationship classification: repeated pain pattern
- Confidence: high

### Why

The evidence shows recurring confusion and support burden around a workflow, not one duplicate ticket or a single incident. The pain may be documentation, onboarding, or UX-related.

### Support handling

- Link tickets: maybe, if helpful for support reporting
- Merge tickets: no
- Keep separate: yes
- Escalate: no, unless volume or impact increases
- Include in reporting: yes
- Next workflow: zendesk-knowledge-candidate-review; use zendesk-backlog-trend-analysis only if the requested deliverable is queue-level reporting, volume, trend, ageing, SLA-risk, or backlog health analysis

## Example 4: Broader incident pattern

### Input pattern

- Ticket ZD-10031: Customer A reports that password reset emails stopped arriving at 09:15.
- Ticket ZD-10032: Customer B reports no transactional emails from the same product area at 09:22.
- Ticket ZD-10033: Customer C reports order confirmation emails are delayed at 09:29.
- The tickets involve different customers and different email types, but all started within a short window.
- Internal notes mention a possible email delivery provider degradation, but no final root cause yet.

### Classification

- Relationship classification: broader incident pattern
- Confidence: medium

### Why

The timing, multi-customer spread, and shared email-delivery surface suggest a coordinated operational issue. The root cause is not fully proven, so confidence should not be high yet.

### Support handling

- Link tickets: yes, to an incident/problem record if that is support practice
- Merge tickets: no
- Keep separate: yes, to preserve customer communication and impact tracking
- Escalate: yes, if provider degradation or service impact is still active
- Next workflow: zendesk-customer-escalation or zendesk-evidence-collector depending on whether intervention or proof is needed first

## Example 5: Inconclusive

### Input pattern

- Ticket ZD-10041: Customer says, "The importer is broken again."
- Ticket ZD-10042: Another customer says, "Import failed this morning."
- No import source, product area, error message, time zone, site URL, file type, account, or recent change is visible.
- Metadata is incomplete and there are no internal notes yet.

### Classification

- Relationship classification: inconclusive
- Confidence: low

### Why

The wording is similar, but there is not enough evidence to determine whether the failures share a symptom, cause, affected workflow, timing, or resolution path.

### Support handling

- Link tickets: maybe later
- Merge tickets: no
- Keep separate: yes
- Escalate: not yet
- Next workflow: zendesk-evidence-collector or zendesk-triage-router
- Smallest missing evidence: error message, affected import type/source, timestamp, site/account, and whether either failure is reproducible

## Example 6: Same customer, similar wording, separate handling needed

### Input pattern

- Ticket ZD-10051: Organisation C reports that a team member cannot access the admin area after a role change.
- Ticket ZD-10052: Organisation C reports that a different team member cannot edit a custom content type after migration.
- Both tickets say "user permissions are broken".
- The first concerns login/admin access; the second concerns editorial capabilities for a specific content type.
- Different users, different expected permissions, and different recent changes are involved.

### Classification

- Relationship classification: related but distinct
- Confidence: high

### Why

The same customer and similar wording do not prove a duplicate. Each case needs separate evidence and may require a different fix.

### Support handling

- Link tickets: yes, as related permissions issues for the same organisation
- Merge tickets: no
- Keep separate: yes
- Escalate: not yet
- Next workflow: zendesk-evidence-collector if permissions history or role mapping must be reconstructed

## Example 7: Possible incident, but proof missing

### Input pattern

- Ticket ZD-10061: Customer A reports payment gateway timeout.
- Ticket ZD-10062: Customer B reports checkout spinning indefinitely.
- Ticket ZD-10063: Customer C reports failed payment callback.
- All arrive within 45 minutes.
- No metadata confirms the same gateway, region, plugin version, or hosting environment.
- There is no provider status evidence yet.

### Classification

- Relationship classification: inconclusive
- Confidence: low to medium

### Why

The timing suggests a possible broader incident, but the shared cause is not established. Classifying as an incident too early could overstate the evidence.

### Support handling

- Link tickets: maybe, under a monitoring/internal note rather than final incident classification
- Merge tickets: no
- Keep separate: yes
- Escalate: not yet, unless active revenue impact is high
- Next workflow: zendesk-evidence-collector
- Smallest missing evidence: gateway/provider, region, affected checkout path, exact timestamps, status-page signal, and recent deployment/config changes

## Example 8: Similar customer language, different root causes

### Input pattern

- Ticket ZD-10071: Customer A says "the site is slow". Evidence shows a large unoptimised hero image on one landing page.
- Ticket ZD-10072: Customer B says "the site is slow". Evidence shows admin dashboard timeouts after a plugin update.
- Ticket ZD-10073: Customer C says "the site is slow". Evidence shows third-party ad scripts delaying article pages.
- The tickets occur across unrelated sites and different workflows.

### Classification

- Relationship classification: repeated pain pattern
- Confidence: medium

### Why

The broad complaint is similar, but the observed causes differ. This is not a duplicate or incident pattern. It may still be useful as a recurring support theme around performance expectations.

### Support handling

- Link tickets: no, unless using reporting tags or a support theme view
- Merge tickets: no
- Keep separate: yes
- Escalate: no, unless one case has urgent customer impact
- Include in reporting: yes, as a recurring performance-support theme
- Next workflow: zendesk-backlog-trend-analysis only if support wants queue-level reporting, volume, trend, ageing, SLA-risk, or backlog health analysis

## Calibration reminders

- Similar wording is not duplicate proof.
- Same customer does not automatically mean one case.
- Same timing does not automatically prove an incident.
- Repeated confusion is often a knowledge or onboarding signal, not a defect.
- Keep customer-level tickets separate when separate communication, impact tracking, or evidence is needed.
- Lower confidence when Zendesk evidence, metadata, or root-cause proof is missing.
