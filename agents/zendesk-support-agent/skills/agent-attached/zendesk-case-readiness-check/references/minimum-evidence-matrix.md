Use this reference when the readiness threshold is unclear. The goal is practical sufficiency, not perfect certainty.

| Target deliverable | Must have | Can proceed without | Blocker example |
|---|---|---|---|
| Customer reply | Clear customer ask, relevant ticket context or supplied evidence, supportable answer or focused clarification, appropriate urgency and tone | Full root cause, final fix, complete historical analysis | Actual customer ask is unclear or the reply would require guessing a knowable fact |
| Internal escalation | Affected customer or account, impact or risk, support checks attempted, specific escalation ask, known unknowns | Complete diagnosis, final remediation plan | Receiving owner would need to restart basic support discovery |
| Knowledge drafting | Stable issue, confirmed resolution/workaround/policy/process, clear audience, repeatability, public/internal boundary | Every edge case, exhaustive support history | Issue is unresolved, unstable, or public guidance could mislead customers |
| Downstream engineering/product handoff | Affected environment or workflow, observed vs expected behaviour, reproduction context or examples, impact, support actions attempted, explicit requested action | Proposed technical fix, certainty about root cause | Reproduction context is missing but support can still obtain it |

## Practical threshold notes

- A customer reply can be ready before root cause is known if the message is honest and useful.
- An escalation can be ready before diagnosis is complete if impact and the internal ask are clear.
- A knowledge draft should wait when the issue, workaround, or public boundary is still unstable.
- A downstream engineering/product handoff needs more confirmed facts than ordinary triage.
