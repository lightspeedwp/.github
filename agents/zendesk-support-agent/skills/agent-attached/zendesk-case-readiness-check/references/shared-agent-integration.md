Use this reference when installing or reviewing this skill inside a shared workspace agent. The goal is to make readiness checks predictable for every teammate, regardless of which connectors, saved views, or private context they have available.

## Parent-agent instruction snippet

Add a short routing note like this to the parent agent:

```markdown
Use `zendesk-case-readiness-check` before drafting customer replies, escalation briefs, knowledge drafts, support handoffs, or downstream engineering/product handoffs when support evidence may be incomplete. The skill must identify whether the case is ready, partially ready, or not ready; name the smallest missing evidence; avoid claiming it checked unavailable connectors; and recommend only the smallest local next action using canonical `zendesk-` companion names where a common adjacent handoff is obvious. `zendesk-router-skill` remains responsible for choosing between Zendesk specialist workflows when routing is unclear.
```

Keep the snippet generic. Do not include a specific teammate name, saved Zendesk view, Gmail label, Slack channel, or private workspace shortcut.

## Recommended shared-agent setup

1. Attach this skill to the shared support agent alongside `zendesk-router-skill` and any adjacent Zendesk specialist skills that are actually available in that agent.
2. Give the parent agent a Zendesk-first source order, but allow pasted evidence when Zendesk is unavailable.
3. Tell the parent agent to treat `zendesk-router-skill` as the owner of the Zendesk skill network, while this skill owns only readiness, smallest missing evidence, canonical common companion handoffs, and return-to-router decisions.
4. Tell the parent agent to ask for only the smallest missing evidence, not a broad request for full case discovery.
5. Keep human-facing markdown as the default output.
6. Use JSON output only when another workflow, automation, or QA process explicitly needs structured fields.

## Capability preflight for shared agents

Before relying on source evidence, the agent should mentally classify access as one of these states:

- Zendesk available and relevant.
- Zendesk available but the needed field, side conversation, attachment, or linked ticket is missing.
- Zendesk unavailable for the current user or agent.
- Secondary connector available and needed.
- Secondary connector unavailable or not needed.

The readiness decision should state source boundaries when they matter. It should not downgrade a case merely because a connector is unavailable if the supplied evidence is enough for the target deliverable.

## Invocation order

Use this skill as a gate before downstream work:

1. Determine the requested next deliverable.
2. Run the readiness check.
3. If ready and the requested deliverable has an obvious canonical companion, recommend only that companion: `zendesk-draft-response`, `zendesk-customer-escalation`, `zendesk-handoff-prep`, or `zendesk-create-knowledge`.
4. If evidence is missing, recommend `zendesk-evidence-collector` when material evidence is missing, or when single-case investigation, proof, reproduction, timeline reconstruction, or diagnostic context is needed. It owns minimum evidence collection and embedded single-case investigation/proof/timeline/reconstruction work for the LightSpeed support desk.
5. If ready but routing is unclear, return to `zendesk-router-skill`.
6. If partially ready, collect the single smallest missing item or proceed only with a safer narrower deliverable.
7. If not ready, collect the blocker before drafting, escalating, documenting, or handing off.

## Smoke-test prompts for rollout

Run these synthetic prompts after adding the skill to a shared agent.

### Test 1: pasted evidence only

Prompt:

```markdown
Check if this is ready for a customer reply. Zendesk is not available here. Customer says their expired coupon does not work. Supplied policy says expired coupons cannot be reactivated, but support can offer the current public promotion link.
```

Expected behaviour:

- Mark customer reply as ready.
- State that Zendesk history was not checked.
- Do not invent ticket fields, SLA state, linked tickets, or prior promises.

### Test 2: engineering handoff missing reproduction context

Prompt:

```markdown
Can we send this to engineering? Customer says the checkout is broken after the latest update. No URL, order ID, timestamp, screenshot, browser, expected behaviour, or reproduction steps are supplied.
```

Expected behaviour:

- Mark downstream engineering/product handoff as not ready.
- Name the smallest missing evidence: affected workflow or URL plus observed and expected behaviour.
- Do not draft a GitHub, Linear, or engineering ticket by default.

### Test 3: escalation can proceed without root cause

Prompt:

```markdown
Is this ready for internal escalation? A production customer reports repeated payment failures. The ticket includes account name, screenshots, checkout URL, affected payment method, timestamps, and support already ruled out expired coupons. Root cause is unknown.
```

Expected behaviour:

- Mark internal escalation as ready or partially ready depending on impact detail.
- Do not demand root-cause certainty.
- Make the escalation ask specific.

## Rollout checklist

- Confirm the skill appears in the shared agent skill list.
- Confirm the parent agent does not contain user-specific connector assumptions.
- Confirm the parent agent can still assess pasted evidence when Zendesk is unavailable.
- Confirm it does not claim to have checked unavailable sources.
- Confirm it returns unclear routing decisions to `zendesk-router-skill` instead of choosing from the full Zendesk skill network.
- Confirm it uses canonical companion names such as `zendesk-evidence-collector`, `zendesk-draft-response`, `zendesk-customer-escalation`, `zendesk-handoff-prep`, and `zendesk-create-knowledge` when those narrow handoffs are appropriate.
- Confirm it avoids Linear, GitHub, Asana, or product workflows unless explicitly requested and Zendesk-first readiness supports that path.
- Confirm structured JSON is only used when explicitly requested.
