Use this file to store **confirmed recurring client, site, and project defaults** that should carry across future work.

Keep this file organized by reusable default set, not by one-off task.

## Core LightSpeed defaults

### Business and service context

- Company name: LightSpeed
- Website: <https://lightspeedwp.agency
- Company type: WordPress website design and development company
- Core service focus: websites for specific client types, with design-to-implementation continuity

### Common project types

- Ecommerce websites
- Tour operator websites
- Publishing websites such as magazines or newspapers

### Default source hierarchy

1. Figma and design-system files for intended design direction
2. Code and repository reality for current implementation truth
3. Product docs and internal documentation for requirements and business rules
4. Research inputs for user needs and behavioral evidence
5. Stakeholder input for goals, constraints, and preferences

### Default accessibility baseline

- WCAG 2.2 AA
- Mobile-first usage
- Strong contrast
- Keyboard support
- Screen-reader compatibility
- Plain language by default
- Readability and interaction clarity for older users

### Default deliverable preferences

- Design briefs and page briefs
- Prioritized critiques
- Broader design and UX audits
- Reference-site analysis
- Bounded implementation handoffs
- WordPress-oriented handoffs when upstream intent is stable

### Brand-sensitive defaults

- Voice should be plain-spoken, genuine, educational, and informal yet respectful.
- Tone should be clear, supportive, and specific.
- Prefer clarity over cleverness.
- Explain technical concepts in accessible language.
- Avoid jargon, hype, fluff, and exaggerated claims.

### WordPress handoff defaults

- Keep recommendations scoped to the requested surface first.
- Prefer the shortest buildable recommendation that answers the request.
- Make states, dependencies, open questions, and acceptance criteria explicit when relevant.
- Do not imply implementation readiness when upstream design intent is still incomplete.

## Reusable client-pattern starters

### Client pattern: WooCommerce store owner

- Primary goals: improve trust, product discovery, and conversion.
- Common surfaces: homepage, category pages, product pages, cart, checkout, account area.
- Common constraints: theme limitations, plugin dependencies, variable product complexity, editor constraints.
- Priority UX concerns: trust, information hierarchy, CTA clarity, product comparison, checkout friction.

### Client pattern: Tour operator website owner

- Primary goals: improve booking clarity, trust, and itinerary comprehension.
- Common surfaces: homepage, tour listings, package pages, itinerary pages, inquiry forms, booking flow.
- Common constraints: long-form content, booking-engine limitations, seasonal offers, mobile-heavy traffic.
- Priority UX concerns: scanability, pricing clarity, reassurance, CTA visibility, information overload.

### Client pattern: Publishing website owner

- Primary goals: improve readability, navigation, engagement, and subscription conversion.
- Common surfaces: homepage, article pages, category pages, search, subscription prompts.
- Common constraints: dense content, ad placements, editorial workflows, legacy templates.
- Priority UX concerns: reading comfort, hierarchy, discovery, interruption management, subscription prompting.

## How to use this file

- Add new sections for real recurring clients, sites, or product lines when patterns become stable.
- Save only confirmed defaults that are likely to matter again.
- Move decisions from active work here only after they prove durable.

## What does not belong here

- one-off task notes
- unresolved follow-ups
- copied review outputs
- speculative assumptions not yet confirmed
