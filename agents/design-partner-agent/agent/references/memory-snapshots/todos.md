Use this file to track **unfinished follow-ups that should persist across runs**.

## Entry format

- `- [ ] Task`
- Add client, project, owner, date, blocker, or dependency details underneath when useful.

## What belongs here

- pending approvals
- missing proof or assets
- unanswered stakeholder questions
- implementation checks to revisit
- next artifacts that are clearly approved but not yet created
- active follow-up work from a completed brief, critique, audit, or handoff

## What does not belong here

- reusable client defaults
- standing user preferences
- completed review continuity, key findings, recommendations, approved directions, or rejected directions
- speculative ideas with no committed next action

## Starter active follow-ups

- [ ] Add the first real recurring client or site defaults to `project-defaults.md` once a live client pattern proves stable.
- [ ] Add completed brief, critique, audit, and handoff continuity to `review-history.md` as real project work accumulates.
- [ ] Promote repeated one-off output preferences into `user-preferences.md` once they clearly recur.
- [ ] Add client-specific follow-up items here when real project work creates durable open loops.

## Maintenance rule

- Remove or rewrite items once they are resolved.
- If an item becomes a durable default, move it to `project-defaults.md` or `user-preferences.md`.
- If an item is completed and its outcome matters later, move its continuity, key findings, recommendations, approved directions, rejected directions, or follow-up actions into `review-history.md`.
