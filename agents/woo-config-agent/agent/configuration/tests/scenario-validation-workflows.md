Use this file for scenario-based validation coverage of the WooCommerce Configuration Agent.

These scenarios are meant to test realistic workflows, not just isolated file rules. Use them alongside the validator pack when maintainers change instructions, references, schemas, prompt-library routing notes, examples, memory guidance, or output expectations.

## Recommended usage

1. Run `bash scripts/run-master-validation.sh` first.
2. Review relevant scenario sections below for the workflow that changed.
3. Compare the agent output against the expected behaviour and failure conditions.
4. Refresh prompts, references, schemas, or validation guidance when scenario behaviour drifts.

## Scenario 1 — File-first site discovery

### Goal

Verify that the agent produces a grounded discovery summary before broader WooCommerce advice when site evidence is available.

### Input shape

- the user asks for a site audit or store-state check
- connected site access is available
- attached reference files are present

### Expected behaviour

- the agent starts with connected-site inspection before broad advice
- the output includes:
  - environment reviewed
  - WooCommerce verification
  - current site signals
  - material limitations
  - recommended next step
- claims stay tied to direct evidence or clearly labelled limitations
- route ownership stays with `woocommerce-site-discovery` until enough evidence exists for a later audit or planning route

### Common failure cases

- generic audit framework appears before inspection
- WooCommerce is assumed rather than verified
- payment, shipping, tax, or checkout behaviour is overstated

## Scenario 2 — Store audit and classification

### Goal

Verify that the agent classifies store state correctly and distinguishes confirmed findings from assumptions.

### Input shape

- the user asks whether the store is launch-ready or wants a WooCommerce audit
- current site evidence is partial or mixed

### Expected behaviour

- the agent states the environment and evidence sources used
- the output distinguishes:
  - confirmed findings
  - material limitations
  - store-state classification
  - priority-ranked actions
- if WooCommerce is not confirmed, the agent switches into reduced audit mode instead of pretending a full audit was completed
- route ownership stays with `woocommerce-audit-orchestrator` when the main job is the audit output itself

### Common failure cases

- launch verdicts without sufficient evidence
- no store-state classification
- risks and findings merged without evidence separation

## Scenario 3 — Implementation planning output

### Goal

Verify that implementation-planning outputs remain practical, scoped, and evidence-based.

### Input shape

- the user asks for a scoped implementation plan, handoff, phased delivery plan, or validation checklist
- the task includes audit findings, discovery outputs, or advisory recommendations that need structured follow-through

### Expected behaviour

- the output states:
  - what evidence or findings it is based on
  - what should happen first
  - what should happen later
  - what still needs validation
  - what risks or assumptions remain
- the output stays with `woocommerce-implementation-planner` unless the user is specifically asking for prioritised remediation sequencing
- the plan does not invent unsupported writes or pretend implementation already happened

### Common failure cases

- reporting completed changes instead of a plan
- folding remediation sequencing into generic planning without showing priority logic
- missing validation or risk notes

## Scenario 4 — Remediation triage and sequencing

### Goal

Verify that remediation requests route into a prioritised fix sequence instead of generic implementation advice.

### Input shape

- the user asks what to fix first, how to phase the work, or how to separate blockers from follow-up items
- the workflow includes multiple findings, dependencies, or unresolved risks

### Expected behaviour

- the output uses `woocommerce-remediation-triage` as the main route
- the output distinguishes:
  - blockers
  - follow-up work
  - dependency-sensitive items
  - validation checkpoints
  - safest sequencing
- the output remains WooCommerce-first and tied to the original evidence set

### Common failure cases

- remediation work is folded into generic implementation planning only
- blockers and later improvements are mixed together
- dependency order is missing or implied instead of stated

## Scenario 5 — Yoast route ownership

### Goal

Verify that Yoast requests stay on the correct Yoast route and do not blur planning work with audit or edit work.

### Input shape

- the user asks for Yoast review, setup planning, troubleshooting, validation planning, or approved Yoast changes
- the site is WordPress or WooCommerce-based

### Expected behaviour

- existing-setup audit, review, retest, completed-change validation, and proposed-edit review route to `yoast-auditor`
- first-time setup planning, reusable strategy, configuration guidance, troubleshooting, validation planning, documentation, and implementation-ready playbooks route to `yoast-configuration`
- if the request mixes planning and approved edit work, the planning or review output is made clear before implementation routing is named
- general WooCommerce audits do not drift into Yoast-specific work unless Yoast becomes the main workstream

### Common failure cases

- Yoast planning is routed as a generic audit
- live or approved Yoast edits are left on the planning route
- broad WooCommerce work is recast as Yoast work without clear trigger

## Scenario 6 — Gravity Forms route ownership

### Goal

Verify that Gravity Forms requests stay on the correct route and do not get blurred into broad WooCommerce or generic WordPress work.

### Input shape

- the user asks for a Gravity Forms audit, readiness review, planning, troubleshooting, validation, or approved form-change work

### Expected behaviour

- read-only audit, readiness review, findings report, retest, and client-safe handoff route to `gravity-forms-auditor`
- planning, configuration, troubleshooting, validation, documentation, and approved implementation change work route to `gravity-forms-configuration`
- broad WooCommerce audits do not get recast as Gravity Forms work unless forms become the main workstream or the user explicitly asks for Gravity Forms-specific work

### Common failure cases

- all forms work routes to one skill regardless of audit vs configuration intent
- a broad store audit is treated as a Gravity Forms task without a clear trigger
- approved form-change work is left on the read-only audit route

## Scenario 7 — Accessibility evidence triage and safe remediation

### Goal

Verify that accessibility-specific work routes cleanly into the accessibility workflow without being mistaken for a broad WooCommerce audit or unsafe WordPress implementation pass.

### Input shape

- the user provides Accessibility Checker findings, an export, screenshots, or asks for accessibility review on a WooCommerce-related site area
- the accessibility issue materially affects product content, forms, checkout clarity, trust, or customer usability

### Expected behaviour

- the agent uses `wordpress-accessibility-checker` as the main route
- the output distinguishes:
  - confirmed accessibility evidence
  - likely user impact
  - safe content-level fixes
  - unsupported theme, plugin, JavaScript, CSS, ARIA, checkout-engineering, or PDF work that must be handed off
- the agent does not claim plugin findings alone prove full WCAG compliance
- approved content-level fixes are separated clearly from broader development remediation

### Common failure cases

- accessibility work is treated as a generic WooCommerce audit finding only
- plugin findings are treated as automatic truth
- unsupported development remediation is presented as a safe direct edit
- the output overclaims compliance or verification certainty

## Scenario 8 — Maintenance workflow handling

### Goal

Verify that internal agent-upkeep requests stay on the maintenance workflow instead of being routed into delivery skills.

### Input shape

- the user asks to audit, document, validate, repair, inventory, or refresh this agent's own files, prompts, references, schemas, tests, scripts, README files, connector guide, or instruction routing

### Expected behaviour

- the agent keeps the maintenance workflow primary
- the output stays focused on the agent's own assets and structure
- prompt-library files, validation docs, and file inventories are treated as maintenance assets
- normal WooCommerce, Yoast, Gravity Forms, or accessibility delivery skills are not used as the main route unless the user separately asks for delivery work

### Common failure cases

- internal maintenance work is routed into a domain delivery skill
- prompt-library upkeep is omitted from the maintenance scope
- the maintenance pass drifts into generic WordPress consulting

## Scenario 9 — Memory updates

### Goal

Verify that durable memory guidance stays clean and scoped.

### Input shape

- the agent needs to remember stable project defaults, blockers, or project history

### Expected behaviour

- durable preferences go to `user-preferences.md`
- active unresolved work goes to `todos.md`
- major factual milestones go to `project-history.md`
- temporary scratch notes are not treated as durable memory

### Common failure cases

- one-off notes stored as durable defaults
- completed tasks left in active sections
- bulky evidence copied into memory files

## Scenario 10 — Follow-up and open-loop handling

### Goal

Verify that the agent handles unresolved follow-up work cleanly without losing scope.

### Input shape

- the user asks for next steps after an audit or partial implementation
- the workflow still has unresolved blockers or missing evidence

### Expected behaviour

- open loops are clearly identified
- next steps are practical and prioritised
- unverified areas are named directly
- follow-up work stays tied to the original WooCommerce outcome
- remediation sequencing requests route to `woocommerce-remediation-triage` instead of being folded into generic implementation advice

### Common failure cases

- vague follow-up guidance
- unresolved blockers hidden inside narrative prose
- drift into unrelated site work

## Final review checklist

Before closing a validation pass, confirm that:

- the validator pack passed or failures were intentionally resolved
- the relevant scenario still matches the current instructions, prompt library, and examples
- schemas, examples, references, and saved recurring prompts do not conflict
- the agent remains WooCommerce-first in both outputs and maintenance docs
- maintenance requests stay on the maintenance workflow while delivery requests stay on the correct routed local skill
