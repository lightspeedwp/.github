## Purpose

This file documents the apps and runtime tools currently used by the WooCommerce Configuration Agent, what evidence they provide, and when maintainers should prefer files or Memory over live app calls.

Use this as a maintenance reference for instruction updates, validation work, and app-usage consistency checks.

## App map

This section covers the currently grounded apps and runtime tools used by the agent.

### Google Drive

**Used for**

- project documents and delivery assets
- Google Docs, Sheets, and Slides used in planning, reporting, and handoff

**Evidence provided**

- project briefs
- implementation notes
- spreadsheets and slide decks
- stored client-facing deliverables

**Practical boundaries**

- treat Drive files as document evidence, not proof of live site behaviour
- document contents may be stale or aspirational
- use direct site inspection before making strong claims about current WooCommerce state

**Prefer files or Memory when**

- the rule or standard is stable and should live in attached references
- a durable preference or long-running project note belongs in Memory
- repeated guidance should be attached to the agent instead of fetched ad hoc

### GitHub

**Used for**

- repository inspection and technical verification tied to WooCommerce implementation
- checking code, file structure, issues, and pull requests when repo evidence matters

**Evidence provided**

- source files
- issue and PR context
- technical implementation history
- repo-level configuration evidence

**Practical boundaries**

- repository state does not prove the current live site matches deployed behaviour
- code evidence should be separated from confirmed runtime behaviour
- use repo evidence to support technical conclusions, not to fake live verification

**Prefer files or Memory when**

- stable coding standards or recurring implementation rules should live in attached references
- durable project defaults or recurring decisions should be remembered across runs

### Bugherd

**Used for**

- QA issue tracking tied to WooCommerce fixes and review work
- recording or reviewing feedback items and bug status

**Evidence provided**

- bug reports
- QA notes
- issue status and follow-up context

**Practical boundaries**

- Bugherd reports are evidence of reported issues, not proof that a bug is still reproducible
- use live site inspection when current runtime behaviour must be confirmed

**Prefer files or Memory when**

- a recurring QA standard or checklist should be preserved as an attached file
- durable follow-up context or stable project preferences should be kept in Memory

### Linear

**Used for**

- project tracking and follow-up task management
- documenting or reviewing planned work tied to WooCommerce delivery

**Evidence provided**

- issue records
- status tracking
- delivery planning context
- ownership and workflow state

**Practical boundaries**

- task state does not prove implementation quality or live store behaviour
- use Linear to support coordination, not as the sole evidence source for audit conclusions

**Prefer files or Memory when**

- the information is stable guidance rather than task state
- a recurring delivery preference or ongoing project note should persist in Memory

### KWV-Dev-Site

**Used for**

- direct WordPress and WooCommerce site inspection
- checking plugins, themes, posts, pages, settings, media, and WooCommerce entities
- supported implementation work when the user explicitly asks for direct changes

**Evidence provided**

- live or directly inspectable site state
- WooCommerce products, orders, customers, reviews, and store configuration signals
- plugin, theme, content, and option-level evidence

**Practical boundaries**

- prefer read-first investigation
- do not overstate what was verified if a specific area was not inspected directly
- writes are higher risk and should follow explicit user intent
- if WooCommerce cannot be confirmed, switch to reduced audit mode rather than assuming normal store behaviour

**Prefer files or Memory when**

- the information is a durable rule, checklist, or reference standard
- the information is a long-running project preference rather than live site evidence

### Web search

**Used for**

- up-to-date public information when internal files and connected tools are not enough
- verifying public documentation, vendor guidance, or current external references

**Evidence provided**

- public web pages
- vendor documentation
- public release or product information

**Practical boundaries**

- public sources do not replace direct site inspection for environment-specific claims
- use web evidence carefully when current attached references already define the agent's internal standard

**Prefer files or Memory when**

- the guidance is stable and should become part of the agent's attached reference layer
- a durable project default should be remembered instead of re-searched

## Source-priority guidance

Prefer sources in this order when the task is maintenance or validation work:

1. current attached files and grounded agent instructions
2. direct connected-site evidence from KWV-Dev-Site when live site state matters
3. attached app evidence from Drive, GitHub, Bugherd, or Linear when that source is directly relevant
4. Memory for durable project continuity
5. web search for public, current external information

Do not let app results override the attached file tree when the task is documenting this agent's own maintained assets.
