## Purpose

Use this file as a repeatable grounded context reference for preview tests, intake reviews, planning reviews, source reviews, drafting handoffs, and workflow-routing checks related to the LSX Design System website, design-system library, and implementation reference set.

## Core references

- Product name: LSX Design System
- Live product site: <https://lsx.design/>
- Demo site: <https://demo.lsx.design/>
- GitHub repository: <https://github.com/lightspeedwp/lsx-design-2025>
- Google Drive documentation folder: <https://drive.google.com/drive/folders/1UTTSaKxs8qc0mgrNyq2_Wt2c18pqSIA_?usp=drive_link>
- LSX Figma design system: <https://www.figma.com/design/U3MB5DRLxHpQDoDs2Pi2jG/-Library--LSX-DS?m=auto&node-id=0-1&t=zNuowvH4BvNuGS3i-1>

## Project profile

- Project type: design-system product plus implementation reference site
- Primary context shape: component-system review, source-of-truth selection, and implementation-alignment planning
- Main comparison surfaces: public product site, demo experience, repository source, approved documentation, and Figma design-system library
- Best fit for: component audits, pattern-governance reviews, design-versus-build comparison, documentation-readiness review, and next-step routing before implementation or content decisions

## Suggested uses

Use this context when testing:

- whether design-system decisions should come from Figma, GitHub, Drive, or the public site
- whether the demo reflects the current intended system or just a comparative build state
- whether implementation evidence matches the documented component and pattern intent
- whether the available sources are strong enough for review, planning, or launch-facing recommendations
- whether the agent can separate current public-facing messaging from underlying component and implementation authority
- whether the agent recommends the right next workflow before drafting, rebuilding, or QA review

## Operational focus areas

When using this project context, prioritise these operational questions:

- what is genuinely confirmed about the LSX system across the live site, demo, implementation source, and Figma library
- which source should control component intent, pattern behaviour, implementation truth, and public-facing messaging
- whether the current material supports design-system review only, implementation review, planning work, or a stronger approval-style assessment
- where the biggest authority conflicts sit between documented intent, coded implementation, and publicly visible behaviour
- which single upstream workflow should run next if the project needs clearer source control before downstream drafting, QA, or launch decisions

## Source-priority notes

When using this context in previews or workflow tests, prefer sources in this order unless the specific task says otherwise:

1. Google Drive documentation folder for approved specs, content, and project documentation
2. GitHub repository for implementation-facing source material
3. Figma design system for component intent, visual-system rules, and interaction-reference context
4. Live product site for current public-facing behaviour and messaging
5. Demo site for comparative review and implementation-experience checks

## Operational source roles

Use the sources this way during repeatable tests:

- Google Drive folder: approved project context, planning inputs, decision history, and documentation that may settle authority disputes
- GitHub repository: implementation evidence, structure, naming, and delivery clues for how the system is currently built
- Figma design system: intended component behaviour, visual rules, layout logic, and reusable pattern direction
- Live product site: current public-facing messaging, visible information architecture, and real published behaviour
- Demo site: comparison surface for identifying implementation differences, preview behaviour, or alternate system expression

## Working assumptions for repeatable tests

Use these as temporary assumptions unless the active prompt says otherwise:

- the Drive folder is the strongest approval-oriented source when a decision, rule, or priority needs confirmation
- the repository is stronger than the public site for implementation-truth questions
- the Figma design system is stronger than the public site for component intent, pattern behaviour, and visual-system direction
- the live product site is stronger than the demo for judging current public-facing messaging and published experience
- the demo may be useful for spotting differences or incomplete alignment, but should not automatically override approved documentation, Figma intent, or repository evidence
- unsupported claims about accessibility, performance, consistency, readiness, or system completeness should be treated as unconfirmed until backed by an approved source

## Recommended preview scenarios

This context is best suited for previews that test:

- design-system source-of-truth selection
- component and pattern review discipline
- design-versus-build comparison logic
- documentation-readiness and approval-readiness judgement
- implementation-alignment review
- next-workflow recommendation quality when authority is split across multiple sources

## Example prompt seed

Use LSX Design System as the project context. Review the live site, demo site, repo, documentation folder, and design-system references. Tell me what context is confirmed, what is still missing, what the safest current assumptions are, the best workflow to run next, the readiness state, what should be saved only if confirmed, and the single best next step.

## Companion prompt variant

Use LSX Design System as the project context. Compare the live site, demo site, repo, Drive folder, and Figma system. Explain which sources should control planning, implementation, and design-system review, identify the biggest gaps or conflicts, and recommend the one workflow that should happen next.
