## Purpose

Use this file as a repeatable grounded context reference for preview tests, intake reviews, planning reviews, source reviews, drafting handoffs, and workflow-routing checks related to the TourOperator.solutions product and demo ecosystem.

## Core references

- Product name: TourOperator.solutions
- Live product site: <https://touroperator.solutions/>
- Demo site: <https://tourpress.pro/>
- Dev site: <https://touroperator-solutions.lightspeedwp.dev/>
- GitHub repository: <https://github.com/lightspeedwp/touroperator-solutions-2025>
- Google Drive documentation folder: <https://drive.google.com/drive/folders/1rygt8TXj0-26u9yi3j_suf5PdsC37XPH?usp=drive_link>
- Tour Operator Figma design system: <https://www.figma.com/design/1wiwltz5a0og0YIoKsuPmn/-Library--TO-DS?node-id=0-1&t=H5LKavfymr9XzKa8-1>

## Project profile

- Project type: tourism product and website platform
- Primary context shape: product-site planning plus implementation-reference review
- Likely working surfaces: live site, demo site, dev site, repository, Drive documentation, and Figma design system
- Best fit for: tourism website planning, content-structure review, source-of-truth checks, implementation review, and launch-readiness assessment

## Suggested uses

Use this context when testing:

- website intake and planning reviews
- source-of-truth and content-collection workflows
- product-site and demo-site comparison tasks
- launch-readiness and QA planning
- GitHub, Drive, and Figma source-review tasks
- website-content routing and next-step recommendations

## Operational focus areas

When using this project context, prioritise these operational questions:

- what is already confirmed across the product, demo, and development surfaces
- which source should control planning, implementation, and content decisions
- whether the current material is strong enough for planning, drafting, review, or launch QA
- where the biggest source gaps, authority conflicts, or approval gaps still sit
- which single upstream workflow should run next before downstream drafting or delivery work

## Source-priority notes

When using this context in previews or workflow tests, prefer sources in this order unless the specific task says otherwise:

1. Google Drive documentation folder for approved specs, content, and project documentation
2. GitHub repository for implementation-facing source material
3. Figma design system for design-system and component-reference context
4. Live product site for current public-facing reference
5. Demo site for product demonstration reference
6. Dev site for in-progress environment checks

## Operational source roles

Use the sources this way during repeatable tests:

- Google Drive folder: approved planning inputs, content notes, documentation, and decision context
- GitHub repository: implementation-facing structure, technical source material, and delivery clues
- Figma design system: visual system, component intent, and design-reference checks
- Live product site: current public-facing behaviour and messaging reference
- Demo site: experience comparison and product-demo review
- Dev site: in-progress validation and environment-check reference

## Working assumptions for repeatable tests

Use these as temporary assumptions unless the active prompt says otherwise:

- the Drive folder is the strongest approval-oriented source
- the repository is stronger than the live site for implementation questions
- the live site is stronger than demo or dev for current public-facing messaging checks
- the demo and dev sites may expose useful differences, but should not automatically override approved documentation
- any unsupported tourism, pricing, performance, or outcome claims should be treated as unconfirmed until backed by an approved source

## Recommended preview scenarios

This context is best suited for previews that test:

- intake-stage routing and missing-information detection
- source-of-truth selection and source-priority reasoning
- product-site versus demo-site comparison logic
- planning-readiness and approval-readiness judgement
- next-workflow recommendation quality
- tourism-project content and implementation review discipline

## Example prompt seed

Use TourOperator.solutions as the project context. Review the live product site, demo site, repo, documentation folder, and design system references. Tell me what context is confirmed, what is still missing, what the safest current assumptions are, the best workflow to run next, the readiness state, what should be saved only if confirmed, and the single best next step.

## Companion prompt variant

Use TourOperator.solutions as the project context. Compare the live site, demo site, dev site, repo, Drive folder, and Figma system. Explain which sources should control planning, implementation, and launch review, identify the biggest gaps or conflicts, and recommend the one workflow that should happen next.
