## Purpose

Use this file as a repeatable grounded context reference for preview tests, intake reviews, planning reviews, source reviews, drafting handoffs, and workflow-routing checks related to the LightSpeedWP.Agency website, design system, and WordPress delivery ecosystem.

## Core references

- Product name: LightSpeedWP.Agency
- Live agency site: <https://lightspeedwp.agency>
- Figma prototype site: <https://lightspeedwp.figma.site>
- Dev site: <https://ls-agency.lightspeedwp.dev/>
- GitHub theme repository: <https://github.com/lightspeedwp/ls-theme>
- GitHub plugin repository: <https://github.com/lightspeedwp/ls-plugin>
- Google Drive documentation folder: <https://drive.google.com/drive/folders/1GqKn_lys_AfPnwI-m3k00C5j0Um6TKAz?usp=drive_link>
- Figma design system: <https://www.figma.com/design/OTqchq3sRBzUy6TICruzc3/LightSpeedWP-Design-System?m=auto&t=CTYQGLlYaOao2LYR-6>
- Figma Make prototype: <https://www.figma.com/make/xAYHN3wsPM4TR2JppUr8sp/LightSpeedWP.Agency?t=CTYQGLlYaOao2LYR-6>

## Project profile

- Project type: agency website plus reusable WordPress design-system delivery stack
- Primary context shape: source-of-truth review, website-content planning, and Figma-to-WordPress implementation alignment
- Main comparison surfaces: live agency site, prototype site, dev site, approved documentation, theme and plugin repositories, and the Figma system
- Best fit for: agency-site planning, service and positioning review, component and pattern review, launch-readiness assessment, and next-step routing before drafting or implementation changes

## Suggested uses

Use this context when testing:

- whether LightSpeed positioning, service architecture, and CTA logic are actually confirmed by the strongest sources
- whether the live site, prototype, dev site, Figma system, and WordPress implementation sources are aligned or drifting
- whether a task should start with source review, content collection, launch QA planning, or another upstream workflow
- whether the agent can separate design intent, implementation truth, and public-facing messaging without mixing their authority
- whether the available materials are strong enough for planning, drafting, review, or launch-facing recommendations
- whether the agent recommends the right next workflow before editing page copy, structure, or component behaviour

## Operational focus areas

When using this project context, prioritise these operational questions:

- what is genuinely confirmed about the agency site across the live environment, prototype surfaces, implementation source, and approved documents
- which source should control positioning, service-page intent, implementation truth, component behaviour, and public-facing messaging
- whether the current material supports planning work only, implementation review, launch QA review, or a stronger approval-style assessment
- where the biggest authority conflicts sit between approved documentation, repository implementation, Figma intent, and visible site behaviour
- which single upstream workflow should run next if the project needs clearer source control before drafting, QA, or release decisions

## Source-priority notes

When using this context in previews or workflow tests, prefer sources in this order unless the specific task says otherwise:

1. Google Drive documentation folder for approved specs, content, strategy, and project documentation
2. GitHub theme and plugin repositories for implementation-facing source material and WordPress delivery truth
3. Figma design system and Figma Make prototype for component intent, layout logic, and prototype-reference context
4. Live agency site for current public-facing messaging and visible behaviour
5. Figma prototype site for prototype-reference comparison
6. Dev site for in-progress environment checks and pre-release validation

## Operational source roles

Use the sources this way during repeatable tests:

- Google Drive folder: approved project context, planning inputs, decision history, content notes, and documentation that may settle authority disputes
- GitHub theme repository: theme structure, templates, block implementation clues, and delivery evidence for the agency site
- GitHub plugin repository: plugin-based behaviour, reusable functionality, and implementation dependencies that may affect the site experience
- Figma design system: intended visual system, reusable components, layout rules, and design-direction reference
- Figma Make prototype: interactive and prototype-oriented expression of design intent and journey flow
- Live agency site: current public-facing messaging, information architecture, visible CTA paths, and published behaviour
- Figma prototype site: comparison surface for prototype-to-live differences
- Dev site: in-progress validation surface for checks that should not override approved documentation by default

## Working assumptions for repeatable tests

Use these as temporary assumptions unless the active prompt says otherwise:

- the Drive folder is the strongest approval-oriented source when a decision, rule, or priority needs confirmation
- the theme and plugin repositories are stronger than the live site for implementation-truth questions
- the Figma system and Figma Make prototype are stronger than the live site for component intent, layout logic, and design direction
- the live site is stronger than prototype or dev for judging current public-facing messaging and published experience
- the dev site and prototype surfaces may expose useful differences, but should not automatically override approved documentation or repository evidence
- unsupported claims about service scope, proof, performance, launch readiness, or implementation completeness should be treated as unconfirmed until backed by an approved source

## Recommended preview scenarios

This context is best suited for previews that test:

- agency-site source-of-truth selection
- service architecture and positioning review
- Figma-versus-build comparison logic
- WordPress implementation-alignment review
- launch-readiness and QA-routing judgement
- next-workflow recommendation quality when authority is split across documentation, Figma, repos, and visible site behaviour

## Example prompt seed

Use LightSpeedWP.Agency as the project context. Review the live site, prototype site, dev site, theme and plugin repos, documentation folder, and Figma references. Tell me what context is confirmed, what is still missing, what the safest current assumptions are, the best workflow to run next, the readiness state, what should be saved only if confirmed, and the single best next step.

## Companion prompt variant

Use LightSpeedWP.Agency as the project context. Compare the live site, prototype site, dev site, theme repo, plugin repo, Drive folder, and Figma references. Explain which sources should control planning, implementation, launch review, and public-facing messaging, identify the biggest gaps or conflicts, and recommend the one workflow that should happen next.
