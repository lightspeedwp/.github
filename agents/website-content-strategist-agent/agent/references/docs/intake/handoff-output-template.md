## Purpose

This file is the current-state packaging template for handing work from an intake, routing, review, claim, approval, or readiness step into the next downstream workflow.

Use it when the current step is not the final destination and the next person, workflow, or specialist step needs a clean working pack that separates:

- confirmed context
- provisional or defaulted context
- approved sources
- source limitations
- open blockers
- claim or risk dependencies
- approval state
- Memory-safe carry-forward items
- the exact next action to take

This template prevents downstream work from treating provisional intake as approved truth.

---

## Core rules

- A handoff must separate confirmed facts from inferred or defaulted assumptions.
- A handoff must not imply approval that has not happened.
- A handoff must name open blockers instead of hiding them in notes.
- A handoff must keep claim-sensitive, approval-sensitive, privacy-sensitive, legal-sensitive, and exclusion-sensitive items visible.
- A handoff must say what the next workflow should do, not just what the current workflow observed.
- A handoff must not silently promote provisional values into durable Memory.
- If the downstream step depends on approved sources, the handoff must say which sources are approved and which are reference-only.

---

## When to use this template

Use this template for handoffs such as:

- intake to drafting
- onboarding to page or project intake
- intake to voice-and-tone strategy
- intake to conversion-goal strategy
- intake to content collection planning
- intake to FAQ or stats intake
- stats or FAQ intake to claim review
- claim review to drafting
- governance review to policy drafting or chatbot planning
- review to approval routing
- readiness review to launch QA or blocker resolution

---

## Required handoff sections

Every handoff should include these sections.

### 1. Handoff summary

State in 2 to 4 lines:

- what this work is
- what stage has just been completed
- what the downstream workflow should do next
- what major caution or dependency still matters most

### 2. Confirmed context

Include only confirmed or approved context that the downstream workflow can rely on.

Typical items:

- confirmed project or task type
- confirmed page or workflow scope
- confirmed primary goal
- confirmed audience
- confirmed approved sources
- confirmed exclusions
- confirmed conversion goal or CTA direction
- confirmed approval owner if known

### 3. Working assumptions and defaults

List anything still inferred or defaulted.

For each item, say:

- the assumption
- whether it is inferred or defaulted
- whether the downstream workflow may use it provisionally
- whether it must be confirmed before a specific next step

### 4. Relevant sources

List the sources the downstream workflow should use, grouped by status:

- approved sources
- approved with limits
- reference-only sources
- pending-review sources

Where useful, add a short note about what each source is safe for.

### 5. Key evidence and extracted tokens

Summarise the most important extracted evidence or structured tokens.

Typical items:

- audience
- offer
- services or products
- design direction
- technical requirements
- approved sources
- exclusions
- claims
- approval owners
- launch or handoff requirements
- missing blockers

Only include what materially helps the next workflow.

### 6. Open blockers and missing inputs

List only the missing points that still materially affect downstream quality, safety, approval, or readiness.

Mark each as one of:

- blocking
- confirm now
- proceed with labelled gap
- safe default for now

### 7. Claims, risks, and exclusions

Summarise the constraints the downstream workflow must not ignore.

Typical items:

- claim-sensitive statements needing review
- unsupported proof areas
- legal or privacy cautions
- exclusions or must-not-do rules
- governance constraints
- launch-readiness risks

### 8. Approval and readiness state

State clearly which of these applies:

- planning_ready
- review_ready
- approval_ready
- approved_for_use
- blocked_from_approval

Then explain any limits on that readiness state.

### 9. Memory-safe carry-forward

List only the values that are safe to carry forward as memory candidates or confirmed reusable defaults.

Group them by:

- current-run only
- project memory candidates
- confirmed reusable memory
- do not save yet

### 10. Exact next workflow

Name the single next workflow that should run first.

Then specify:

- what that workflow should do
- what inputs it should rely on
- what it must not assume
- what it should return or produce

## Readiness language rules

### Use planning_ready when

- the handoff is useful for planning or routing only
- major approvals or validations are still pending
- downstream work should treat the pack as structured context, not approval

### Use review_ready when

- the pack is ready for stakeholder or specialist review
- open issues are visible and contained
- the next step is evaluation, not direct publication or sign-off

### Use approval_ready when

- the pack is properly structured for a sign-off decision
- relevant evidence, source posture, and claim posture are attached clearly
- the approval owner can reasonably decide from this pack

### Use approved_for_use when

- approval has actually been given
- the approved scope is explicit
- the downstream workflow may rely on the approved parts within that scope

### Use blocked_from_approval when

- material blockers, claim gaps, source gaps, or exclusions still prevent a valid approval state
- the handoff would otherwise mislead the downstream workflow about readiness

---

## Handoff quality checks

Before sending a handoff, check that:

- confirmed facts are not mixed with defaults
- source approval state is explicit
- claim-sensitive items are not buried
- exclusions are visible where they matter
- readiness state is explicit and not overstated
- Memory-safe and not-safe items are separated clearly
- the next workflow is singular and actionable
- the pack states what the downstream step should return

## Example handoff

```md
---
status: review_ready
handoff_type: intake_to_drafting
next_workflow: page drafting
---

# Handoff pack

## Handoff summary

The initial page-intake step is complete for a service page draft.
The page goal, audience direction, and approved strategy brief are strong enough for structured drafting.
Two proof claims still need review before the page can be treated as publish-ready.
The next workflow should draft the page structure while keeping those proof items provisional.

---

## Confirmed context

- Page type: service page
- Primary goal: generate consultation enquiries
- Audience: operations leaders at growing service businesses
- Approved source: strategy brief v3
- Confirmed exclusion: do not use unsupported ranking claims

---

## Working assumptions and defaults

- Tone direction is inferred as clear and expert — inferred — usable provisionally for draft wording
- Secondary CTA is defaulted to a lower-friction resource route — defaulted — confirm before final CTA lock-in

---

## Relevant sources

### Approved sources
- Strategy brief v3 — safe for page goals, audience direction, and messaging priorities

### Reference-only sources
- Website briefing questionnaire — safe for intake context and missing-field detection only
- Live homepage URL — safe for orientation, not for claim approval

---

## Key evidence and extracted tokens

- audience: operations leaders at growing service businesses
- primary_goal: generate consultation enquiries
- offer: strategy-led website delivery
- exclusions: no unsupported proof claims
- claims: trusted-by and performance-improvement wording present

---

## Open blockers and missing inputs

- Proof claim validation for two visible trust statements — confirm now
- Secondary CTA destination confirmation — safe default for now

---

## Claims, risks, and exclusions

- Do not use rankings, guarantees, or quantified performance wording without approved evidence
- Current visible trust claims are not yet approved for publication

---

## Approval and readiness state

- review_ready for structured drafting
- not approved_for_use as final public copy until proof claims are reviewed

---

## Memory-safe carry-forward

### Current-run only
- provisional CTA direction

### Project memory candidates
- confirmed primary goal
- confirmed audience

### Confirmed reusable memory
- none yet

### Do not save yet
- inferred tone direction
- unreviewed proof claims

---

## Exact next workflow

- Workflow: page drafting
- Use these inputs:
  - strategy brief v3
  - confirmed audience and primary goal
  - exclusion against unsupported proof claims
- Do not assume:
  - that visible homepage trust claims are approved
  - that the default secondary CTA is final
- Return:
  - a structured service page draft with proof-sensitive areas clearly controlled

---
```
