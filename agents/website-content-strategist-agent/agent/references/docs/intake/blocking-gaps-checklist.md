## Purpose

This file is the current-state decision guide for identifying which missing inputs should:

- stop the workflow
- trigger one focused clarification question
- stay visible as a labelled gap while the work proceeds
- be handled with a safe temporary default for the current run only

Use it to keep intake concise without hiding material uncertainty.

---

## Core rule

Ask only for missing information that materially changes:

- the goal of the work
- the correct workflow or routing path
- the source authority needed
- the scope boundary
- the output type or destination
- the claims, approvals, exclusions, or risk posture
- whether reusable Memory would be safe

If a missing detail does not materially change one of those, prefer a labelled default or proceed with caution instead of stalling.

---

## Gap outcomes

| Outcome | Meaning | Action |
|---|---|---|
| blocking | The workflow cannot continue reliably without this input. | Stop and ask one focused question. |
| confirm_now | The workflow can partially proceed, but this specific point must be confirmed before a material next step. | Continue only up to the confirmation boundary. |
| proceed_with_labelled_gap | The workflow can continue if the gap stays visible. | Proceed and mark the gap clearly. |
| safe_default_for_now | A temporary default is acceptable for this run. | Use the default, label it, and do not treat it as confirmed truth. |

---

## Blocking-gap test

Treat a missing input as **blocking** when the answer would materially change:

1. which specialist workflow should run first
2. what the user is actually trying to accomplish
3. which source or authority is safe to rely on
4. whether the work is page-level, section-level, full-site, policy, chatbot, launch, or governance work
5. whether public-facing claims, approvals, exclusions, or risk controls are required before proceeding
6. whether the next output should be planning, review, drafting, claim review, approval routing, or launch gating

If the missing input would only improve polish, convenience, or preference handling, it is usually not blocking.

---

## Checklist by gap type

### 1. Goal and task gap

- [ ] Is the primary goal known?
- [ ] Is the immediate task type known?
- [ ] Is the user asking for planning, review, drafting, governance, FAQ work, stats intake, claim review, or launch readiness?
- [ ] Would a different answer send the work into a different specialist workflow?

Use **blocking** when the task could route into materially different workflows.
Use **proceed_with_labelled_gap** when the broad direction is clear enough and only sub-preferences are missing.

### 2. Workflow-context gap

- [ ] Is this a new initiative, active-project continuation, or one-off task?
- [ ] Is the current project stage known well enough?
- [ ] Does the workflow depend on whether intake, strategy, drafting, review, or launch comes next?

Use **blocking** when the missing context changes which upstream stage should happen first.
Use **safe_default_for_now** when a conservative upstream-first default can be used without harm.

### 3. Source-authority gap

- [ ] Are the key sources known?
- [ ] Is the approval status of those sources known where it matters?
- [ ] Would the output become misleading if the wrong source were treated as authoritative?
- [ ] Is a questionnaire, screenshot, public URL, or rough note being mistaken for approved truth?

Use **blocking** when approved-source authority is required for the next real step.
Use **confirm_now** when drafting structure can proceed but factual or reusable content cannot.
Use **proceed_with_labelled_gap** when source uncertainty can stay visible in a planning-only output.

### 4. Scope-boundary gap

- [ ] Is the scope page, section, full-site, policy set, chatbot plan, or launch review?
- [ ] Would the answer change effort, workflow, or output structure materially?
- [ ] Is there a risk of silently expanding the task?

Use **blocking** when the scope ambiguity would lead to the wrong deliverable.
Use **safe_default_for_now** only when the smallest useful scope is clearly safer and reversible.

### 5. Audience and conversion gap

- [ ] Is the audience known?
- [ ] Is the intended user action or conversion goal known?
- [ ] Would the absence of this context weaken structure, CTA logic, proof use, or FAQ planning materially?

Use **confirm_now** when early planning can proceed but real drafting quality depends on confirmation.
Use **blocking** when the requested output is high-stakes drafting and audience or goal is missing.
Use **proceed_with_labelled_gap** for review-style outputs that are meant to surface the missing strategy.

### 6. Claims and risk gap

- [ ] Are any claim-sensitive statements present?
- [ ] Are stats, testimonials, comparisons, guarantees, rankings, ROI, performance, or regulated implications involved?
- [ ] Is the evidence or approval state missing?

Use **blocking** when the workflow is about public-facing proof or validation.
Use **confirm_now** when content structure can continue but claim wording cannot be finalized.
Use **harder review paths** from the risk and review checklist when the gap creates trust or compliance risk.

### 7. Exclusions and must-not-do gap

- [ ] Are important exclusions known?
- [ ] Is the workflow missing a must-not-do rule that could change the output materially?
- [ ] Could the absence of this exclusion create overreach, unsafe advice, or unsupported claims?

Use **blocking** when the missing boundary affects safety, legality, compliance, or truthfulness.
Use **proceed_with_labelled_gap** when the output is an intake or review artifact that explicitly flags the boundary as unresolved.

### 8. Approval-owner gap

- [ ] Is it clear who approves claims, policy wording, launch readiness, or source reuse?
- [ ] Would the next output falsely imply readiness without this owner being known?

Use **confirm_now** when the work can continue as planning only.
Use **blocking** when the output would otherwise be treated as launch-ready, publish-ready, or approved.

### 9. Memory-safety gap

- [ ] Is the value stable enough for future reuse?
- [ ] Is it confirmed, or still inferred/defaulted?
- [ ] Would saving it now create misleading durable memory?

Use **confirm_now** when the work can continue but Memory promotion must wait.
Use **safe_default_for_now** when the value only needs to guide the current run.
Never treat this gap as resolved just because the value seems plausible.

## One-question rule

When a gap is blocking, prefer one focused question that unlocks the next correct move.

Good examples:

- **What was this questionnaire intended to help capture for this workflow?**
- **Is this source approved for reuse in the working output, or should I treat it as reference-only for intake?**
- **Should I treat this as a single-page task or a full-website planning task?**
- **Is the main goal here to generate enquiries, support bookings, or clarify information for existing users?**

Avoid broad multi-question forms when one answer would resolve the next step.

---

## Safe-default rules

A gap may use **safe_default_for_now** only when:

- the default does not create a misleading claim
- the default does not widen scope materially
- the default does not imply approval that has not happened
- the default does not create unsafe durable Memory
- the default remains clearly labelled as provisional

Typical safe defaults:

- smallest useful scope
- review-style output instead of final drafting
- neutral professional tone
- questionnaire values kept as inferred/defaulted only
- claim-sensitive wording routed to review instead of published directly

---

## Proceed-with-gap rules

A workflow may continue with a labelled gap when:

- the current output is planning, review, routing, or intake-focused
- the missing detail does not yet force a wrong workflow choice
- the missing detail is visible in the output
- the output does not pretend the gap is resolved

Typical examples:

- a review summary that identifies missing approved sources
- a project brief draft with unresolved audience confirmation
- a handoff pack that names open claim-review dependencies

## Example decisions

### Example: blocking

**Gap:** unclear whether the request is for a single service page or a full website plan.

**Decision:** blocking

**Why:** this changes routing, output structure, effort, and likely specialist workflow.

**Focused question:**

- Should I treat this as a single-page task or a full-website planning task?

---

### Example: confirm now

**Gap:** audience is inferred from the brief, but not confirmed.

**Decision:** confirm_now

**Why:** planning can continue, but final CTA logic and messaging direction may change materially.

**Action:** proceed with a labelled audience assumption until the confirmation point.

---

### Example: proceed with labelled gap

**Gap:** source approval owner is not yet known.

**Decision:** proceed_with_labelled_gap

**Why:** a review summary can still be useful if it clearly flags the unresolved approval dependency.

---

### Example: safe default for now

**Gap:** no explicit output shape was requested for an early planning query.

**Decision:** safe_default_for_now

**Why:** a structured review-style output is a reversible, low-risk default for the current run.
