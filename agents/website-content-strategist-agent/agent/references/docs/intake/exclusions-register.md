## Purpose

This file is the current-state working register for recording scope boundaries, must-not-do rules, unsupported areas, prohibited claims, and other explicit exclusions that should shape intake, drafting, review, approval, routing, and Memory decisions.

Use it to distinguish between:

- what is clearly in scope
- what is conditionally allowed
- what must be excluded from the workflow
- what needs review before it can be included
- what should never be promoted into durable reusable defaults without confirmation

This register complements the source approval and evidence-token references.

- The source approval register answers: **Is the source safe to rely on?**
- The evidence-token schema answers: **What did we extract from the source?**
- This exclusions register answers: **What must not be done, assumed, promised, or reused?**

---

## Core rules

- Treat exclusions as operational constraints, not optional notes.
- If a source, questionnaire, or user message suggests a prohibited action, unsafe claim, or unsupported area, capture it here before proceeding.
- Prefer explicit exclusions over broad hidden assumptions.
- If an exclusion conflicts with a default, the exclusion wins.
- If an exclusion conflicts with a weaker source, the stronger approved authority wins.
- Do not save inferred exclusions as durable reusable memory without confirmation unless they come from an approved controlling source.
- Where possible, write exclusions in action-oriented language so they can guide downstream workflows clearly.

---

## Exclusion statuses

| Status | Meaning | Use |
|---|---|---|
| confirmed | Explicitly confirmed by the user or a stronger approved authority. | Safe to enforce as a real boundary. |
| inferred | Likely boundary inferred from questionnaire, source pattern, or workflow context. | Use cautiously in the current run and confirm when material. |
| defaulted | Safe temporary boundary applied to avoid overreach in the current run. | Keep current-run only unless later confirmed. |
| missing | A boundary likely matters here, but has not been established yet. | Ask only if it is blocking or risk-bearing. |
| unsupported | The requested area or behaviour is outside safe or supported scope. | Do not proceed as if allowed. |

---

## Exclusion types

Common exclusion categories include:

- scope exclusion
- audience exclusion
- content exclusion
- claim exclusion
- legal or privacy exclusion
- approval exclusion
- source exclusion
- workflow exclusion
- publishing exclusion
- integration exclusion
- styling or tone exclusion
- chatbot behaviour exclusion
- launch exclusion
- memory exclusion

---

## Register schema

| Field | Purpose |
|---|---|
| Exclusion label | Short human-readable name |
| Exclusion type | Category of exclusion |
| Status | confirmed, inferred, defaulted, missing, or unsupported |
| Applies to | Project, workflow, page, asset, source, output, chatbot, launch step, or memory item |
| Rule | The actual must-not-do or boundary statement |
| Trigger or context | What caused this exclusion to matter |
| Source basis | User confirmation, approved source, questionnaire, policy, review note, or safe default |
| Enforcement level | hard stop, review required, or current-run caution |
| Affects claims | yes, no, or maybe |
| Affects memory | yes, no, or maybe |
| Notes | Short explanation or next action |

## Typical exclusion patterns

### Scope boundaries

Use when the work should not expand beyond the intended task.

Examples:

- do not turn a single-page content request into a full-website rewrite
- do not assume ecommerce scope for a brochure site
- do not include launch-readiness recommendations when the task is only intake routing unless the user asks

### Claim exclusions

Use when unsupported or risky proof language must be blocked.

Examples:

- do not use guaranteed ranking claims
- do not invent client statistics
- do not reuse testimonials without confirmation and approval
- do not publish performance claims without evidence review

### Legal and privacy exclusions

Use when wording, interpretation, or advice must stay controlled.

Examples:

- do not imply legal compliance guarantees
- do not invent retention periods or data-processing claims
- do not interpret policy requirements as final legal advice

### Source exclusions

Use when a source may guide intake but not serve as approved truth.

Examples:

- do not treat questionnaires as confirmed project truth
- do not treat public website copy as automatically approved
- do not treat screenshots as proof approval

### Tone and styling exclusions

Use when voice or tone boundaries matter.

Examples:

- do not use hype-heavy language
- do not use playful tone for policy pages
- do not use premium-language defaults unless brand positioning confirms them

### Chatbot behaviour exclusions

Use when chatbot scope and escalation limits matter.

Examples:

- do not answer outside approved knowledge scope
- do not imply human review already happened when it has not
- do not provide unsupported legal, financial, medical, or safety guidance

### Memory exclusions

Use when certain values should not become durable defaults.

Examples:

- do not save inferred questionnaire answers as confirmed project memory
- do not save unsupported claims into reusable memory
- do not save temporary routing assumptions as durable project defaults

---

## Enforcement levels

### Hard stop

Use when the workflow should not proceed as requested without changing course.

Typical cases:

- unsupported regulated claims
- clearly prohibited publishing behaviour
- excluded source use that would make the output misleading
- requests that exceed approved scope materially

### Review required

Use when the work may continue only after approval, evidence review, governance review, or stronger confirmation.

Typical cases:

- privacy-sensitive wording
- claim-bearing proof statements
- policy-sensitive chatbot behaviour
- brand defaults that are still inferred

### Current-run caution

Use when a boundary is prudent to observe now but may not need to become a permanent rule yet.

Typical cases:

- temporary scope limits
- provisional exclusions from a questionnaire pattern
- conservative defaults during ambiguous intake

---

## Relationship to claims and Memory

### Affects claims

Mark **Affects claims: yes** when the exclusion blocks or reshapes:

- statistics
- guarantees
- rankings
- comparisons
- awards
- testimonials
- case-study proof
- performance or outcome wording
- compliance or suitability implications

These should usually route into the claim register.

### Affects memory

Mark **Affects memory: yes** when the exclusion means:

- a value must not be saved durably
- a value can only be saved after confirmation
- a boundary itself should become a reusable project constraint once confirmed

Confirmed exclusions can be strong candidates for reusable project memory when they are stable and genuinely important across future related work.

## Example entries

## Exclusion: no unsupported proof claims

- Exclusion type: claim exclusion
- Status: confirmed
- Applies to: public-facing website copy
- Rule: do not use statistics, testimonials, rankings, guarantees, or outcome claims without approved evidence review
- Trigger or context: website drafting and FAQ generation
- Source basis: approved workflow rule
- Enforcement level: hard stop
- Affects claims: yes
- Affects memory: yes
- Notes:
  - if proof is useful but unsupported, route it into claim review rather than removing the issue silently

---

## Exclusion: questionnaires are not confirmed truth

- Exclusion type: source exclusion
- Status: confirmed
- Applies to: intake, drafting, and Memory promotion
- Rule: do not treat questionnaire answers or questionnaire defaults as confirmed project truth without user confirmation or approved-source support
- Trigger or context: questionnaire-aware intake flows
- Source basis: intake framework rule
- Enforcement level: review required
- Affects claims: yes
- Affects memory: yes
- Notes:
  - questionnaire material can inform intake and smart defaults, but not durable truth by itself

---

## Exclusion: no legal certainty from policy drafting

- Exclusion type: legal or privacy exclusion
- Status: confirmed
- Applies to: policy pages and governance outputs
- Rule: do not imply final legal certainty, legal advice, or compliance guarantees in policy or trust-page outputs
- Trigger or context: policy drafting and governance documentation
- Source basis: policy workflow rule
- Enforcement level: hard stop
- Affects claims: yes
- Affects memory: maybe
- Notes:
  - legal or privacy review may still be needed before publication

---

## Exclusion: no durable memory for temporary defaults

- Exclusion type: memory exclusion
- Status: confirmed
- Applies to: Memory promotion
- Rule: do not save temporary routing assumptions, questionnaire defaults, or provisional intake answers as confirmed reusable memory
- Trigger or context: current-run intake and memory promotion
- Source basis: memory framework rule
- Enforcement level: review required
- Affects claims: maybe
- Affects memory: yes
- Notes:
  - move only confirmed stable values into reusable project memory

---

## Review triggers

Escalate or tighten exclusions when:

- a claim-sensitive statement is present without approved support
- a questionnaire default is being treated like confirmed truth
- a source is unapproved but is shaping public-facing output
- a boundary affects legal, privacy, medical, financial, safety, or regulated content
- the request is trying to widen scope beyond the approved workflow
- an inferred exclusion is materially changing the output and should be confirmed
