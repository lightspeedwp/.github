Use this routing map after classifying the project. Choose one primary route and only add secondary routes when they add immediate value.

## Intake, evidence and discovery

| Need | Route to | Use when | Output expected |
|---|---|---|---|
| Evidence harvesting | `project-evidence-harvester` | The user has rough notes, links, emails, docs or site references and needs a clean evidence base before planning. | Evidence base with approved vs unconfirmed sources and explicit gaps. |
| Intake normalisation | `project-intake-evidence-normaliser` | Mixed evidence needs structured intake fields, exclusions and confirmed source notes. | Clean project intake record. |
| Design or implementation execution packet | `design-execution-packet` | Multiple design, repo, website, QA or implementation inputs need one execution-ready packet. | Execution-ready packet with readiness labels and next route. |
| Project research | `lightspeed-project-researcher` | Source evidence needs review before PRD, technical brief or task breakdown. | Source inventory, research summary, assumptions, blockers and PRD-ready notes. |

## PRD, technical planning and implementation

| Need | Route to | Use when | Output expected |
|---|---|---|---|
| Standalone PRD | `lightspeed-prd-generator` | Goals, users, scope, acceptance criteria and risks need to be formalised. | PRD/product brief. |
| Figma-to-WordPress technical brief | `lightspeed-figma-wordpress-technical-brief` | Figma design-system intent must become WordPress architecture, theme/plugin boundaries and implementation guidance. | Developer-ready technical brief. |
| Combined planning pack | `lightspeed-prd-task-manager` | The user explicitly wants a PRD + technical brief + task route from available inputs. | Consolidated planning pack. |
| Task breakdown | `lightspeed-task-breakdown-planner` | PRD/technical brief are approved and implementation tasks or delivery waves are needed. | Epics, tasks, dependencies, acceptance criteria and draft issue structure. |
| Implementation sequencing | `lightspeed-implementation-plan-generator` | Approved tasks need sequencing, branch strategy, workstreams, QA approach and dependency controls. | Developer-ready implementation plan. |
| GitHub issue drafts | `lightspeed-github-issue-drafter` | Approved tasks, bugs or QA findings need GitHub-ready markdown issues. | Issue titles, bodies, labels, milestones and QA notes. |

## Design, Figma and WordPress build routes

| Need | Route to | Use when | Output expected |
|---|---|---|---|
| Design context synthesis | `design-context-synthesis` | Briefs, emails, Figma, repo notes or implementation constraints conflict or need reconciliation. | Clear design context and decision-ready synthesis. |
| Design QA readiness | `design-qa-readiness` | A design doc, brief, layout direction or Figma handoff must be checked before development. | Readiness review with gaps and risks. |
| WordPress block-theme handoff | `wordpress-block-theme-handoff` | Approved design direction must become a WordPress block-theme handoff. | Template, pattern and style guidance. |
| Block-theme asset routing | `wordpress-block-theme-router` | The request is about patterns, templates, template parts, custom templates, block styles or section styles. | Correct specialist asset route. |
| Figma/WordPress parity audit | `lightspeed-figma-wordpress-parity-auditor` | Figma design-system intent and WordPress implementation need comparison. | Parity audit across tokens, blocks, patterns, states and modes. |

## QA, launch and delivery control

| Need | Route to | Use when | Output expected |
|---|---|---|---|
| Requirements traceability | `lightspeed-requirements-traceability-mapper` | Requirements, tasks, issues, acceptance criteria and QA coverage must be mapped. | Traceability matrix and missing coverage notes. |
| Acceptance testing | `lightspeed-acceptance-test-planner` | Test scenarios, validation matrices or QA scripts are needed before build or launch. | Acceptance test plan and validation matrix. |
| Launch QA planning | `lightspeed-launch-qa-planner` | Final launch QA scope needs planning before audits are run. | Launch QA plan, page/template matrix and gates. |
| QA finding triage | `lightspeed-qa-findings-router` | Actual QA findings need severity, ownership, fix routing or retest steps. | Prioritised fix list and retest plan. |
| Launch readiness audit | `lightspeed-launch-readiness-auditor` | Final pre-launch checklist, go/no-go summary or page-by-page QA is required. | Launch readiness report. |
| Launch task routing | `lightspeed-launch-task-router` | Launch work needs routing across redirects, schema, analytics, policy, claims, design parity and QA. | Specialist launch routing report. |
| Release handoff | `lightspeed-release-handoff-generator` | Release notes, handover docs, monitoring plans or support transition notes are needed. | Release/handoff package. |

## Project memory, approvals, change control and reporting

| Need | Route to | Use when | Output expected |
|---|---|---|---|
| Project memory | `lightspeed-project-memory-manager` | A durable memory bank, decision log, task index or assumption register is needed. | Project memory pack. |
| Approval gates | `lightspeed-approval-gate-manager` | Sign-off, stakeholder review, go/no-go criteria or approval control is the next step. | Approval checklist and decision log. |
| Change request | `lightspeed-change-request-router` | Scope changes arrive after PRD, technical brief or tasks have been approved. | Change impact, approval path and risk notes. |
| Project status | `lightspeed-project-status-reporter` | Stakeholders need a status update, blocker summary, risk update or next-action plan. | Status report. |
| Planning review | `lightspeed-prd-task-reviewer` | A PRD, brief, task plan or issue pack needs quality review before implementation. | Readiness and gap review. |
| Pack export | `lightspeed-prd-task-pack-exporter` | Project artefacts need organising into a downloadable or Google-doc-ready pack. | Folder structure, index, archive and review checklist. |

## Routing quality rules

- Prefer the most specific skill over a broader combined workflow.
- Do not route to task, GitHub issue or implementation skills until PRD and technical brief assumptions are approved or explicitly accepted.
- Do not route to launch audit skills when the team only has launch planning inputs; use launch QA planning first.
- Do not route to content generation until source material, claims and approval boundaries are clear.
- Do not route to chatbot planning until source-of-truth, exclusions, escalation and privacy assumptions are captured.
