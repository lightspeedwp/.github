# Accessibility (A11y) Instructions

**Scope**: Organization-wide standard for all code, content, and documentation.
**Baseline**: WCAG 2.2 Level AA (minimum requirement).
**Owner**: LightSpeed Accessibility Team
**Status**: Active

---

## Overview

All LightSpeedWP projects must meet **WCAG 2.2 Level AA** accessibility standards. This file provides practical guidance for developers, designers, and content creators to build inclusive products that work for everyone, including people with disabilities.

### Key Principles

- **Perceivable**: Content must be presentable to users in ways they can perceive (not invisible to all senses)
- **Operable**: Interface components and navigation must be operable via keyboard and other input methods
- **Understandable**: Content and operation must be understandable
- **Robust**: Content must be compatible with assistive technologies

## HTML & Semantic Markup

### Use Semantic HTML

```html
<!-- ✓ Good: Semantic HTML -->
<nav aria-label="Main navigation">
  <ul>
    <li><a href="/">Home</a></li>
    <li><a href="/about">About</a></li>
  </ul>
</nav>

<!-- ✗ Avoid: Divs masquerading as nav -->
<div class="nav">
  <div class="item"><a href="/">Home</a></div>
</div>
```

**Rules**:

- Use `<header>`, `<nav>`, `<main>`, `<article>`, `<section>`, `<aside>`, `<footer>` appropriately
- Use `<button>` for buttons, not `<div onclick="">`
- Use `<a>` for links, not `<span onclick="">`
- Use `<form>`, `<input>`, `<label>` for forms
- Use `<table>`, `<thead>`, `<tbody>`, `<tr>`, `<th>`, `<td>` for tabular data

### Heading Hierarchy

```html
<!-- ✓ Good: Sequential heading levels -->
<h1>Page Title</h1>
<h2>Main Section</h2>
<h3>Subsection</h3>
<h2>Another Section</h2>

<!-- ✗ Avoid: Skipped levels -->
<h1>Page Title</h1>
<h3>Subsection</h3> <!-- Skipped h2! -->
```

**Rules**:

- One `<h1>` per page
- Never skip heading levels (h1 → h2 → h3, not h1 → h3)
- Use headings to structure content, not for styling

## Keyboard Navigation

### Keyboard Support

All interactive elements must be operable via keyboard:

- `Tab` / `Shift+Tab`: Move focus between interactive elements
- `Enter` / `Space`: Activate buttons and links
- `Arrow Keys`: Navigate within lists, menus, and custom components
- `Escape`: Close modals and dropdowns

```html
<!-- ✓ Good: Button is keyboard accessible -->
<button>Submit</button>

<!-- ✓ Good: Custom button with proper ARIA -->
<div role="button" tabindex="0" @click="handle" @keydown.enter="handle" @keydown.space="handle">
  Custom Button
</div>

<!-- ✗ Avoid: Non-interactive element without keyboard support -->
<div @click="handle">Not Keyboard Accessible</div>
```

### Focus Management

```html
<!-- ✓ Good: Visible focus indicator -->
<button style="outline: 2px solid blue; outline-offset: 2px;">Focused Button</button>

<!-- ✓ Good: Skip-to-content link (visible on focus) -->
<a href="#main-content" class="skip-link">Skip to main content</a>

<!-- ✗ Avoid: Removing focus outline without replacement -->
<button style="outline: none;">Can't see focus!</button>
```

**Rules**:

- Never remove focus outlines without providing visible alternative
- Focus order must be logical (top-to-bottom, left-to-right)
- Use `tabindex` sparingly; prefer semantic HTML for tab order
- Provide visible focus indicator with minimum 2px outline or equivalent contrast

## Screen Reader Support

### ARIA Labels & Descriptions

```html
<!-- ✓ Good: Descriptive aria-label -->
<button aria-label="Close dialog">✕</button>

<!-- ✓ Good: aria-labelledby for custom title -->
<div id="dialog-title">Confirm Action</div>
<button aria-labelledby="dialog-title">OK</button>

<!-- ✓ Good: aria-describedby for additional info -->
<input type="password" aria-describedby="pwd-hint">
<p id="pwd-hint">Password must be 8+ characters</p>

<!-- ✗ Avoid: Icon-only button without label -->
<button>🔍</button> <!-- Screen readers say "button" with no context -->
```

### ARIA Roles & Properties

```html
<!-- ✓ Good: Explicit role for clarity -->
<div role="alert">Error: Email already exists</div>

<!-- ✓ Good: aria-expanded for expandable content -->
<button aria-expanded="false" aria-controls="menu">Menu</button>
<ul id="menu" hidden>...</ul>

<!-- ✓ Good: aria-live for dynamic updates -->
<div aria-live="polite">Loading... 50% complete</div>
```

**Rules**:

- Provide alternative text for all icons and images
- Use `aria-label` when text label is not visible
- Use `aria-describedby` for additional context
- Use `role` only when semantic HTML doesn't exist
- Use `aria-live` for updates that don't change focus

### Image Alt Text

```html
<!-- ✓ Good: Descriptive alt text -->
<img src="team-photo.jpg" alt="LightSpeed team at WordCamp 2024">

<!-- ✓ Good: Decorative image marked as such -->
<img src="separator.png" alt="" aria-hidden="true">

<!-- ✗ Avoid: Generic alt text -->
<img src="team-photo.jpg" alt="photo">

<!-- ✗ Avoid: Saying "image of" (screen readers already say "image") -->
<img src="chart.png" alt="Image of annual sales">
```

## Color & Contrast

### Color Contrast Ratios

Minimum contrast requirements (WCAG 2.2 AA):

- Normal text: 4.5:1 (foreground to background)
- Large text (18pt+ or 14pt+ bold): 3:1
- UI components & borders: 3:1

```css
/* ✓ Good: Strong contrast */
.text { color: #000; background: #fff; } /* 21:1 */

/* ✓ Good: Sufficient contrast */
.text { color: #333; background: #fff; } /* 12.6:1 */

/* ✗ Avoid: Insufficient contrast */
.text { color: #ccc; background: #fff; } /* 1.4:1 - FAIL */
```

### Don't Rely on Color Alone

```html
<!-- ✓ Good: Color + text + icon -->
<span style="color: red;">● Error:</span> Invalid email

<!-- ✗ Avoid: Color alone -->
<span style="color: red;">Invalid email</span>
```

**Tools**:

- Use WebAIM Contrast Checker: <https://webaim.org/resources/contrastchecker/>
- Browser DevTools: Lighthouse audit includes contrast checks
- Axe DevTools: Chrome/Firefox extension for accessibility testing

## Form Accessibility

### Labels & Input Association

```html
<!-- ✓ Good: Label associated with input -->
<label for="email">Email:</label>
<input type="email" id="email" name="email" required>

<!-- ✗ Avoid: Label without association -->
<label>Email:</label>
<input type="email" name="email">
```

### Required Fields & Validation

```html
<!-- ✓ Good: Mark required fields -->
<label for="name">Name <span aria-label="required">*</span></label>
<input type="text" id="name" required aria-required="true">

<!-- ✓ Good: Clear error messages -->
<input type="email" id="email" aria-describedby="email-error">
<p id="email-error" role="alert">Email format is invalid. Use user@example.com</p>

<!-- ✗ Avoid: Vague error messages -->
<p>Invalid input</p>
```

## Video & Media Accessibility

### Captions & Transcripts

- **Captions** (CC): Includes spoken dialogue + sound effects for deaf/hard of hearing
- **Subtitles**: Translation or dialogue only (not sufficient for a11y)
- **Transcripts**: Full text version of audio/video content

```html
<!-- ✓ Good: Video with captions -->
<video controls>
  <source src="talk.mp4" type="video/mp4">
  <track kind="captions" src="talk.vtt" srclang="en" label="English">
</video>

<!-- ✓ Good: Provide transcript link -->
<p><a href="/transcripts/talk">Read transcript</a></p>
```

## Animation & Motion

### Prefers Reduced Motion

```css
/* ✓ Good: Respect user motion preferences */
@media (prefers-reduced-motion: reduce) {
  * {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
  }
}
```

**Rules**:

- Avoid auto-playing animations
- Don't use flashing/blinking content (avoid >3 flashes per second)
- Respect `prefers-reduced-motion` media query

## Testing & Validation

### Automated Testing

- **Lighthouse**: Built into Chrome DevTools (Accessibility tab)
- **Axe DevTools**: Free browser extension (Chrome, Firefox, Edge)
- **WAVE**: Web Accessibility Evaluation Tool (browser extension)

### Manual Testing

1. **Keyboard navigation**: Tab through entire page, verify focus visible and logical
2. **Screen reader**: Use NVDA (Windows), JAWS, or VoiceOver (Mac) to test
3. **Zoom**: Zoom to 200%, verify layout remains usable
4. **Color contrast**: Use WebAIM Contrast Checker or Lighthouse

### Test Checklist

- [ ] All interactive elements keyboard accessible
- [ ] Focus order is logical
- [ ] Focus indicator is visible
- [ ] All images have alt text (or `alt=""` if decorative)
- [ ] Form labels associated with inputs
- [ ] Error messages clear and helpful
- [ ] Color contrast ≥ 4.5:1 for normal text
- [ ] Videos have captions & transcripts
- [ ] Page structure uses semantic HTML headings
- [ ] No keyboard trap (can Tab/Shift+Tab out of all elements)
