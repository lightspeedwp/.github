Use this workflow when generating, auditing or updating `DESIGN.md`.

## 1. Triage

Classify the request:

- new project without `DESIGN.md`;
- existing project without `DESIGN.md`;
- existing project with `DESIGN.md`;
- audit-only;
- validation-only;
- export-only.

Choose the smallest output set that satisfies the request.

## 2. Evidence Collection

Collect evidence in this order when available:

1. User-provided files and links.
2. Figma variables, modes, components, variants, frames and design context.
3. GitHub repository files such as `DESIGN.md`, `theme.json`, `styles/*.json`, `block.json`, CSS, Sass, patterns, templates and docs.
4. Brand guides, design-system notes, PRDs and governance documents.
5. Screenshots or live-site evidence, labelled as inferred unless confirmed elsewhere.

Track the source of each major token or rule while you work.

## 3. Normalisation

Sort findings into:

- primitive tokens;
- semantic tokens;
- component tokens;
- brand tokens;
- state tokens.

Note:

- mismatched names;
- duplicated meanings;
- hardcoded implementation values;
- undocumented components;
- inaccessible colour pairings;
- unsupported assumptions.

## 4. Drafting

Build or update:

1. `DESIGN.md`
2. `design-md-source-map.md`
3. `design-md-validation-report.md`

Use YAML front matter for machine-readable tokens and Markdown prose for rationale and usage notes.

Recommended narrative sections:

- `## Overview`
- `## Colors`
- `## Typography`
- `## Layout`
- `## Elevation & Depth`
- `## Shapes`
- `## Components`
- `## Do's and Don'ts`

Preserve existing custom sections when they still add value and the user has not asked to remove them.

## 5. Validation

Run deterministic checks where available:

```bash
designmd spec --rules --format json
designmd lint DESIGN.md --format json
designmd diff DESIGN.md previous-design-md.md --format json
designmd export DESIGN.md --format dtcg
```

Also perform manual checks for:

- source traceability;
- WordPress mapping clarity;
- accessibility and contrast risks;
- editor-safety;
- responsive behaviour notes;
- inferred value labelling;
- portability outside Stitch and plain-text usability in GitHub.

## 6. Reporting

The final report should state:

- which files were created or changed;
- which evidence sources were used;
- which validation checks ran successfully;
- what remains inferred or unverified;
- which follow-up tasks are recommended.
