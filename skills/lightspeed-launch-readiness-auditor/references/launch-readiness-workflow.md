## 1. Confirm launch context

Collect:

- client or project name
- live site URL
- staging/dev site URL
- project type
- launch target date, if known
- whether the launch replaces an existing site
- whether the URL structure changes
- whether ecommerce, memberships, forms, analytics, ads or chatbot features are involved

## 2. Classify evidence

Mark each evidence source as:

| Evidence | Status | Notes |
|---|---|---|
| Live URL list | Received / Pending |  |
| New URL list | Received / Pending |  |
| Redirect map | Received / Pending |  |
| Lighthouse/PageSpeed | Received / Pending |  |
| Accessibility checks | Received / Pending |  |
| Form tests | Received / Pending |  |
| GA4/GTM plan | Received / Pending |  |
| Search Console baseline | Received / Pending |  |
| Policy pages | Received / Pending |  |
| Content approval | Received / Pending |  |

## 3. Audit by workstream

Review:

1. Content approval
2. Navigation and internal links
3. Redirects and SEO migration
4. Forms and conversion paths
5. Analytics and tags
6. Accessibility
7. Performance
8. Mobile/responsive behaviour
9. Security and privacy
10. WordPress admin/editor readiness
11. WooCommerce or payment flows, if relevant
12. Launch-day operational plan

## 4. Decide launch readiness

Use the go/no-go rules. Be conservative when evidence is missing for launch-critical flows.

## 5. Output

Produce a structured report with:

- value, risk and next step
- launch decision
- issue register
- launch blockers
- checklist tables
- post-launch monitoring tasks
